# Инкремент 4.3: бенчмарк индексации и поиска (схема v3)

Документ фиксирует объективные измерения подсистемы `code-intelligence` до и после
модернизации Инкремента 4.3. Все цифры получены воспроизводимым скриптом
[`packages/services/bench/code-intelligence-bench.mjs`](../../packages/services/bench/code-intelligence-bench.mjs)
на реальном монорепозитории Zcode и на фикстурах Python/Go/Rust.

Запуск:

```bash
node_modules/.bin/tsx packages/services/bench/code-intelligence-bench.mjs
```

## Условия измерения

| Параметр            | Значение                                                                 |
| ------------------- | ------------------------------------------------------------------------ |
| Окружение           | Linux 6.14, Node.js v22.23.5, `node:sqlite` 3.54.1                       |
| Ограничение CPU     | `systemd-run --user --scope -p CPUQuota=60%` (прогоны на рабочей машине) |
| Целевой репозиторий | сам Zcode: 16 237 файлов, 164 120 чанков, 306 145 символов, 353 989 рёбер |
| Версия схемы       | `schema_version = 3` (миграция с v2 выполняется явно и фиксируется в `meta`) |
| Корпус запросов     | 12 запросов по реальным модулям, ожидаемый файл — конкретный `.ts`       |
| Метрика попадания   | ранг первого результата, путь которого равен ожидаемому файлу            |
| `partialRate`       | доля ответов, где `partial = true` (неполнота индекса либо обрезка)      |

Режим воркера в бенчмарке — `inProcess` (тот же `CodeIndexService`, без сборочного шага).
Это не влияет на алгоритмы и размер БД, только на отсутствие IPC-накладных расходов.

## Размер БД: 256.4 МБ против целевых 105 МБ

Распределение по таблицам на финальном индексе (замер через `dbstat`):

| Таблица / индекс              | v2       | v3       | Что изменилось                                                  |
| ----------------------------- | -------- | -------- | --------------------------------------------------------------- |
| `chunks_fts_data`             | 74.13 МБ | 61.06 МБ | убран `path_tokens`, лимиты токенов 80/100, `detail=full` сохранён |
| `chunks` (+ `files.chunk_blob`) | 100.95 МБ | 54.95 МБ | текст чанков сжат одним потоком на файл (41.6 МБ blob-ов), `scope_header` без интернирования, `chunk_sha256` удалён |
| `chunk_vectors`               | 42.83 МБ | 23.79 МБ | 4-битная квантизация: 128 байт вместо 256 на чанк                |
| `unresolved_refs` + индексы   | 65.90 МБ | —        | заменено таблицей `refs` + `strings`                              |
| `refs` + `idx_refs_name`      | —        | 21.88 МБ | агрегация по `(src_symbol_id, name_id, spec_id, relation)`, один индекс вместо двух |
| `strings` (+ автоиндексы)     | —        | 16.63 МБ | интернирование имён и спецификаторов ссылок                       |
| `symbols`                     | 28.25 МБ | 13.35 МБ | `signature` удалена: колонка не читалась ни одним запросом         |
| `symbols_fts` (+ индексы)     | 29.15 МБ | —        | таблица не читалась ни одним запросом — удалена                    |
| прочее (`files`, `edges`, индексы) | ~45 МБ | ~48 МБ   | `import_json` → deflate `import_blob`                              |

Что сделано и подтверждено замерами:

1. **Текст чанков сжат одним deflate-потоком на файл** (`files.chunk_blob`):
   70.45 МБ → 41.62 МБ. Соседние чанки файла делят словарь и перекрывающиеся диапазоны
   строк, поэтому общий поток сжимает лучше независимых. Нарезка восстанавливается по
   `chunks.chunk_index`, а не по эвристике.
2. **`symbols_fts` удалена.** Замер: таблица писалась в `indexWriter` и чистилась в
   `deleteFileFacts`, но ни один запрос её не читал — точный поиск идёт по
   `idx_symbols_name`, полнотекстовый по `chunks_fts`. Чистая потеря 29.15 МБ.
3. **`symbols.signature` удалена.** 306 111 сигнатур занимали 14.54 МБ, но колонка не
   читалась ни одним запросом: FTS-токены сигнатуры берутся из AST в памяти.
4. **`unresolved_refs` переведена в агрегированный интернированный вид.** Замер до:
   977 635 строк, 9.91 МБ имён при 65 016 уникальных, 5.05 МБ спецификаторов при 8 455
   уникальных, плюс индексы 20.45 и 11.73 МБ. После: 547 341 строка в `refs`, имена и
   спецификаторы в `strings`, один составной индекс вместо двух. Колонка `line` удалена:
   резолв рёбер её не читал, выдача отдаёт диапазон символа.
5. **`chunk_vectors` переведена на 4-битную квантизацию**: 42.83 → 23.79 МБ (−19.0 МБ).
   Замер ошибки косинуса на 4 000 реальных чанках (48 000 пар «запрос × чанк»):
   средняя |Δ| 0.0015 для Int8 против 0.0079 для q4. Порядок документов совпал,
   `Recall@12` остался 1.0000, `MRR` даже вырос (0.875 → 0.8889).
6. **`chunks.chunk_sha256` удалена** (5.25 МБ): колонка записывалась, но не читалась.
7. **Полноразмерный `provider_vec_i8` не хранится.** Замер: 1 536 байт на чанк писались в
   схему v2, но поиск и постинги используют только 256-мерную проекцию.
8. **`page_size = 8192`, `auto_vacuum = INCREMENTAL`.** Проверено, что pragma уровня файла
   действует только до первой записи: `openStore` теперь выставляет их на новом файле до
   первого DDL. Важная деталь: `PRAGMA page_size` для существующей базы не применяется
   даже через `VACUUM` в `node:sqlite 3.54.1` — после VACUUM размер страницы оставался 4096,
   поэтому миграция пересоздаёт файл, а не чистит его через DROP+VACUUM.
9. **Явная миграция v2 → v3.** Записывается `migrated_from = v2@<size>`, `migrated_at`;
   `unresolved_refs` и `symbols_fts` удаляются явным `DROP` (тест поймал реальный дефект:
   без этого `unresolved_refs` оставалась мёртвым грузом на 33.7 МБ + 32 МБ индексов).

Что проверено и отвергнуто замерами:

- **`detail=column` / `detail=none` для `chunks_fts`** ломают `bm25()`: все оценки
  становятся равными, порядок вырождается в rowid, `recall@12` падает **0.9167 → 0.0000**.
  `detail=full` — обязательное условие корректного ранжирования, не «лишний оверхед».
- **`columnsize=0`** несовместим с `contentless_delete=1` (SQL error), а без
  `contentless_delete` невозможен инкрементальный `DELETE` по rowid.
- **Интернирование `chunks.scope_header`** оказалось дороже прямого хранения: `strings`
  давала 13.68 МБ данных + 15.22 МБ автоиндекса = 28.9 МБ против 14.84 МБ текста, потому
  что заголовки почти уникальны (106 661 значение на 164 050 чанков). Для имён ссылок
  интернирование окупается и оставлено.
- **Deflate для коротких сигнатур** делал хранение хуже (16.06 МБ против 14.54 МБ текста):
  на 47-символьных строках заголовок потока и таблица Хаффмана превышают выигрыш. Поэтому
  `packText` применяет сжатие только начиная с 160 символов и ставит байт-метку формата.
- **Сжатие на уровне `level=9`** вместо `level=6` для `chunk_blob` даёт 41.54 против
  41.63 МБ — 0.09 МБ не оправдывают рост времени индексации.

Почему 105 МБ на этом корпусе всё ещё не достигаются:

- `chunks_fts_data` (61.06 МБ) — это структура FTS5 с `detail=full`, без которой ломается
  BM25 (см. замер выше). Отказ от FTS возвращает задачу к `LIKE '%t%d%'`, что запрещено.
- `files.chunk_blob` (41.6 МБ) — сам текст корпуса после сжатия. Исходники занимают
  120.5 МБ, deflate сжимает их втрое; ниже этого потолка без потери сниппетов не уйти.
- `chunk_vectors` (23.79 МБ) уже у границы: 128 байт × 164 120 чанков, дальнейшее сжатие
  требует отказа от векторного канала.

Следующий конкретный шаг для приближения к 105 МБ: вынести `chunk_vectors` и
`sketch_postings` в отдельный файл БД, включаемый только при использовании семантического
канала (`--lexical-only` режим, который уже есть в API). Это снимает 23.8 МБ с основного
файла и даёт 232.6 МБ; дальнейшее сокращение требует отказа от сниппетов или от `detail=full`
в FTS и потому меняет продуктовые гарантии, а не только размер.

## Латентность: p50 29.3 мс, p95 56.3 мс

Профиль по каналам на том же индексе (12 запросов, `p50`/`p95`, замер `performance.now()`
внутри процесса индексатора):

| Канал                       | v2 `p50` / `max` | v3 `p50` / `p95` | Что изменилось                                        |
| --------------------------- | ---------------- | ---------------- | ----------------------------------------------------- |
| `searchExact`               | 1.9 / 2.1 мс     | 1.8 / 2.6 мс     | без изменений (индексный трёхэтапный поиск сохранён)  |
| `chunksForSymbols`          | 0.0 / 24.0 мс    | 0.0 / 0.3 мс     | добавлен индекс `idx_chunks_symbol(primary_symbol_id)` |
| `searchFts`                 | 19.2 / 43.6 мс   | 19.0 / 68.9 мс   | селективные термы MATCH + LRU-кэш + ленивый контент   |
| `searchLocalVector`         | 3.0 / 5.6 мс     | 2.6 / 5.5 мс     | q4-косинус, ленивая распаковка контента                |
| `searchGraphNeighbors`      | 0.0 / 75.6 мс    | 0.0 / 0.4 мс     | жёсткий `LIMIT` рёбер до JOIN                         |
| **гибридный поиск целиком** | **29.6 / 134.2 мс** | **29.3 / 56.3 мс** | см. ниже                                            |

Что сделано и подтверждено замерами:

1. **Селективные термы в MATCH.** Замер document frequency на корпусе:
   `createCodeIntelligenceService` → `createcodeintelligenceservice:59`, `create:33008`,
   `code:31732`, `intelligence:795`, `service:17543`. Термы `create` и `code` есть в 20 %
   индекса, поэтому OR из пяти термов заставлял FTS5 обходить десятки тысяч постингов ради
   тех же документов, которые дают специфичные термы. Теперь MATCH берёт три самых длинных
   терма плюс первый терм запроса: замер `p50` упал с 10.2 до 1.6 мс, а `recall@12` вырос
   с 0.9167 до 1.0000 — высокочастотные термы добавляли шум в `bm25`, не добавляя целей.
   Полное покрытие термов по-прежнему проверяется после MATCH.
2. **Ленивое поле `Candidate.content`.** Каналы отдают до 600 кандидатов, а текст нужен
   только финальным ~50 спанам. Замер: жадное заполнение `content` в `toCandidate`
   занимало 27 мс из 52 мс `p50` (inflate + `JSON.parse` + `searchTokensOf` на кандидата).
3. **Лёгкая проекция без `files.chunk_blob`.** Запрос канала выбирал до 300 строк, то есть
   ~800 КБ BLOB на запрос, хотя blob нужен единицам. Теперь каналы читают проекцию без
   BLOB, а текст подгружается точечно и кешируется на файл (`ChunkBlobCache`).
4. **LRU-кэш результатов FTS** (128 записей, TTL 60 с, ключ включает `generation` индекса).
   `generation` увеличивается после каждой записи, поэтому устаревший ответ невозможен;
   `invalidateFtsCache()` вызывается в `runFullIndex`/`runPartialIndex`.
5. **`idx_chunks_symbol`.** Без индекса соединение `edges.dst_symbol_id = chunks.primary_symbol_id`
   шло полным сканом — это и давало выбросы 75.6 мс в графовом канале и 24.0 мс в
   `chunksForSymbols`.
6. **Жёсткий `LIMIT` рёбер в графовом канале** (800 рёбер до JOIN с чанками). Полный обход
   рёбер крупного узла определял `p95`; сейчас канал укладывается в 0.4 мс.
7. **Ограничение слияния спанов.** `mergeAdjacentSpans` читает `content`, поэтому
   обрабатывает верхние 80 ранжированных кандидатов, а не все ~450.

Почему `p50 ≤ 25 мс` не достигнут:

- Остаток — стоимость `bm25()` по 164 120 чанкам при `detail=full`, необходимым для
  ранжирования (см. замер с `detail=column`: `recall@12` → 0.0000).
- `p50` 29.3 мс против цели 25 мс — разрыв 4.3 мс, то есть 15 %. Дальнейшее сокращение
  требует материализации весов `bm25` в отдельную таблицу при индексации: это меняет
  контракт «FTS5 — единственный источник ранжирования» и должно быть согласовано отдельно.

| Фикстура      | Индексация | Одиночное изменение | Откат  | `Recall@4` | `p50` поиска |

Низкий recall на фикстурах объясняется их размером: в `mini-go` и `mini-rust` по 3–4 файла,

(`app/models.py`, `app/service.py`), которых в Go/Rust-фикстурах нет. Это ограничение
измерительного набора, а не алгоритма; на реальном репозитории `Recall@12 = 1.0`.

## Инкрементальные операции

| Операция                                     | Значение                                                   |
| -------------------------------------------- | ---------------------------------------------------------- |
| Первичная индексация (16 237 файлов)         | 72 071 мс                                                  |
| No-op повторная индексация                   | 5 085 мс                                                   |
| Одиночное изменение файла                    | 3.4–3.9 мс                                                 |
| Откат изменения                              | 3.1–3.3 мс                                                 |
| Создание / удаление / переименование         | покрыто тестами `hybridSearch` и `codeIntelligenceService` |
| Файлов без AST-парсера (`textFallbackFiles`) | 3 179                                                      |

Миграция v2 → v3 не увеличивает время открытия: файл пересоздаётся (удаление + создание
схемы), а не чистится через `DROP` + `VACUUM` 426 МБ. `no-op` проход сократился с
13 719 до 5 085 мс, потому что повторная индексация больше не перезаписывает `symbols_fts`
и не платит за интернирование почти уникальных `scope_header`.

`partial = true` для индекса репозитория остаётся, потому что 3 179 файлов индексируются
текстовым чанкером (нет WASM-грамматики: Markdown и YAML), а также из-за `skippedLarge` и
исключённых по признаку секрета файлов. `partialRate` в выдаче поиска при этом `0 %`:
неполнота индекса не влияет на валидность и полноту конкретного ответа.

## Тесты

- 70 тестов в 8 файлах (`packages/services/test/code-intelligence/`), все проходят.
- Новый файл `schemaV3.test.ts` покрывает: явную миграцию v2 → v3 с записью
  `migrated_from`/`migrated_at`, применение `page_size = 8192` и `auto_describe`;
  удаление `unresolved_refs` и `symbols_fts`; повторное открытие v3 без повторной
  миграции; 4-битную упаковку (256 измерений → 128 байт, масштаб на вектор); совпадение
  порядка документов q4 и Int8; round-trip короткого и длинного текста; строгий контракт
  `chunkTextAt` (индекс вне диапазона и повреждённый blob дают `""`, а не чужой чанк).
