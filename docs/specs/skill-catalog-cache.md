# SkillCatalogCache

## Контекст

- `NodeSkillAdapter.discoverSkills` (`apps/zcode-cli/packages/adapters/src/skills/index.ts`) при каждом вызове
  пересканирует все корни и заново читает каждый `SKILL.md` (`parseSkill`); кеша mtime/size/hash нет.
- Каталог нужен только для метаданных: prompt-секция рендерит `name`/`description`/`whenToUse`
  (`apps/zcode-cli/packages/core/src/context/sections/skills.ts`), discovery в runtime выполняется один раз.
  Тело читается отдельно `loadSkill` c `maxBytes` и должно остаться ленивым.
- `SkillCatalogCache` сокращает файловые чтения на повторных discovery: не изменившийся `SKILL.md`
  не перечитывается, метаданные берутся из памяти.
- Host services (`packages/services/src/skills/service/discovery.ts`) читает тело каждого `SKILL.md`,
  потому что `SkillSummary.body` — публичное поле контракта и уходит UI через RPC. Этот путь кеширует
  только `_meta.json` (не тело); enabled/plugin state читаются из config на каждый вызов.

## Цели

1. Повторный `discoverSkills` с неизменными файлами не делает ни одного чтения `SKILL.md`.
2. Изменение одного файла перечитывает только его; исчезнувшие файлы удаляются из кеша.
3. Тело `SKILL.md` никогда не удерживается в кеше; `loadSkill` читает его по требованию.
4. Кеш ограничен по числу записей и не течёт при долгоживущем runtime.
5. Конкурентные discovery не дублируют чтения одного и того же файла.
6. Публичный `SkillSummary` (включая `body`) не меняется.

## Не цели

- Кеширование тел, permission/plugin enabled state, hook trust, marketplace-состояния и секретов.
- Персистентный кеш между процессами или перезапусками.
- Изменение алгоритма выбора корней, scopes и приоритетов.

## Владельцы состояния и единственный путь записи

### CLI runtime: `NodeSkillAdapter`

- Один экземпляр `NodeSkillAdapter` (создаётся на runtime через
  `apps/zcode-cli/packages/bootstrap/src/skills.ts`) владеет одним `SkillCatalogCache`.
- Единственный писатель — приватный путь `discoverSkills` → loading entry. Никакой другой код
  (tools, marketplace install, subagent port) не пишет в кеш напрямую; все они идут через
  `adapter.discoverSkills` и получают те же записи.
- Кеш живёт в памяти экземпляра адаптера: разные runtime/воркспейсы не делят записи, кеш умирает
  вместе с адаптером.

### Host services: `createSkillsService`

- Один экземпляр `SkillMetadataCache` создаётся внутри `createSkillsService` и передаётся в оба
  вызова `discoverSkills` (`list`, `setEnabled`). `discoverSkills` без кеша работает как раньше.
- Кешируется только результат разбора `_meta.json` по пути и mtime/size. `SKILL.md`-body,
  enabled-map (`config.skills`) и plugin-состояние (`config.plugins`) не кешируются и читаются
  на каждый вызов.

## Ключ каталога и запись

Ключ CLI-кеша — абсолютный путь `SKILL.md` в том виде, в котором его вернул scan root
(без realpath). Это позволяет удалять записи по префиксу корня, не разыскивая реальные пути.
`canonicalPath` (realpath на момент чтения) хранится в записи как идентичность файла.

Запись (тело и полный текст файла не хранятся):

| Поле            | Смысл                                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------- |
| `path`          | ключ: путь `SKILL.md` из scan root                                                                          |
| `canonicalPath` | realpath файла на момент чтения                                                                             |
| `mtimeMs`       | `stat().mtimeMs` на момент чтения                                                                           |
| `sizeBytes`     | `stat().size` на момент чтения                                                                              |
| `contentHash`   | sha256 hex сырых байт файла (диагностика/доказательство)                                                    |
| `metadata`      | `name`/`description`/`whenToUse`/`safeToAutoLoad`/`frontmatterKeys` или `null`, если файл не валидный skill |
| `diagnostics`   | шаблоны диагностик разбора (без IO-ошибок) для повторной выдачи                                             |

Поля, зависящие от корня (`path`, `directory`, `rootPath`, `scope`, `source`, `pluginName`,
`pluginId`, `qualifiedName`, `policy`), в записи не хранятся и собираются при каждом вызове из
текущего `SkillRoot`. Один и тот же файл, найденный через разные корни, получает корректный
scope/namespace.

## Инвалидация и порядок событий

```
discoverSkills:
  scan roots ──► для каждого SKILL.md:
      stat(path)
        ├─ ENOENT ──────────────► пропустить (не кешировать ошибку)
        ├─ stamp == entry.stamp ► hit: 0 чтений, отдать entry + диагностики
        └─ иначе ───────────────► miss/inflight:
                                   readFile ─► parse ─► hash
                                   store(path, newEntry) ─► evict if over limit
  после всех корней:
      для каждого просканированного корня:
          prune entries под корнем, которых не было в scan
```

- Инвалидация — по паре `mtimeMs` + `sizeBytes`: любое изменение одного из них перечитывает
  только этот файл; остальные записи остаются.
- `contentHash` фиксируется, но не является ключом инвалидации: файл с тем же mtime/size не
  перечитывается (осознанный компромисс, см. риски).
- Файл, который исчез из scan, удаляется из кеша по префиксу своего корня. Записи других корней
  не трогаются: `loadSkill` может вызываться с подмножеством roots.
- Ошибки чтения (`EACCES` и т.п.) не кешируются и дают `skill_read_failed` на каждый вызов;
  `ENOENT` между stat и чтением трактуется как «файла нет».

## Ограничение размера

- Размер ограничен числом записей: по умолчанию 512, переопределяется
  `createNodeSkillAdapter({ catalogCacheMaxEntries })` (минимум 1).
- При переполнении вытесняется самая давно использованная запись (LRU на `Map`).
- Запись содержит только пути/числа/короткие метаданные, тело skill не удерживается, поэтому
  верхняя граница памяти предсказуема.

## Конкурентность

- Single-flight по ключу: параллельные `discoverSkills` на одном адаптере разделяют одно
  чтение файла; каждый вызов делает свой `stat` и получает свой массив диагностик.
- Отмена (`AbortSignal`) проверяется между файлами как раньше; отменённый вызов не отменяет
  общее чтение, начатое другим вызовом, и не пишет частичных записей.
- Порядок диагностик детерминирован: сначала диагностики разбора файла, затем диагностики
  теней (`skill_duplicate_name`) в прежнем порядке.

## Разделение CLI runtime и Host UI

| Путь                     | Что кешируется                      | Что читается каждый раз                              |
| ------------------------ | ----------------------------------- | ---------------------------------------------------- |
| CLI `discoverSkills`     | метаданные `SKILL.md` по mtime/size | ничего при hit                                       |
| CLI `loadSkill`          | — (использует hit каталога)         | тело файла по требованию, `maxBytes`                 |
| Host `list`/`setEnabled` | `_meta.json` по mtime/size          | `SKILL.md` тело, `config.skills`, plugin roots/state |

Host не кеширует тело, потому что `SkillSummary.body` — часть публичного контракта, которую
потребляет prompt-сборка и RPC-потребители. Убирать поле или отдавать пустое тело означало бы
тихую поломку контракта, поэтому этот путь оставлен как есть; выигрыш Host-пути — только
`_meta.json` (один файл на skill за вызов).

## Что не кешируется

- Тело `SKILL.md` и результат `loadSkill`.
- `disabledPaths` (задаются при создании адаптера и не меняются).
- `config.skills` enabled-map, `config.plugins` (enabled/dirs/enabledPlugins), plugin roots.
- Диагностики IO-ошибок, marketplace/install-состояние, permissions, hook trust, секреты.
- Отрицательные результаты `_meta.json` (файла нет) — на каждый вызов выполняется stat.

## Acceptance-сценарии

1. Cache hit: второй `discoverSkills` по тем же файлам → 0 чтений `SKILL.md`, тот же результат.
2. Изменение `sizeBytes` или `mtimeMs` одного файла → ровно 1 чтение, обновлённые метаданные,
   остальные файлы не читаются.
3. Новый файл → 1 чтение только нового; удалённый файл → 0 чтений и отсутствие в выдаче.
4. Удалённый и заново созданный файл с прежними mtime/size перечитывается (запись удалена prune).
5. `loadSkill` → ровно 1 чтение тела, `maxBytes`/`truncated` работают как раньше.
6. Один файл через разные roots получает актуальные `scope`/`rootPath`/`qualifiedName` (данные
   корня не кешируются).
7. Невалидный skill (нет description) при повторном discovery не читается и повторяет диагностику.
8. Переполнение кеша (маленький лимит) вытесняет запись: вытесненный файл перечитывается.
9. Конкурентные `discoverSkills` читают каждый файл не более одного раза.
10. Host: второй `list` не читает `_meta.json`, но по-прежнему читает `SKILL.md` (тело не кешируется).
11. Host: изменение `_meta.json` видно на следующем `list`; изменение тела `SKILL.md` видно сразу.
12. Host: включение/выключение skill и plugin в config видно на следующем `list` без пересоздания
    сервиса (state не кешируется).
13. Host: конкурентные `list` не читают один и тот же `_meta.json` больше одного раза.

## Метрика

Число чтений `SKILL.md` на discovery и число чтений `_meta.json` на `list`, плюс время discovery
на тестовом каталоге. Методика: focused vitest с обёрткой `readFile` из `node:fs/promises`,
считающей пути `*/SKILL.md` и `*/_meta.json`; сравнение «первый вызов» / «повторный вызов» на
одном и том же каталоге. Абсолютные цифры зависят от числа skill в каталоге; инвариант — 0
чтений на hit.

## Риски и остаточные ограничения

- `mtimeMs`+`sizeBytes` — не криптографическая инвалидация: правка с тем же размером и
  временем (быстрая запись в одну мс, грубая точность ФС, восстановление из бэкапа) не будет
  замечена до следующего изменения. `contentHash` доступен для диагностики, но не сравнивается
  на hit.
- На сетевых ФС с грубым mtime инвалидация может запаздывать в пределах гранулярности.
- Кеш живёт в экземпляре адаптера; несколько runtime/воркспейсов не разделяют записи, поэтому
  суммарная память линейна по числу живых адаптеров и ограничена 512 записями на адаптер.
- Symlink, переустановленный на другой файл с теми же mtime/size, останется с прежними
  метаданными до изменения stamp.
- Host-путь по-прежнему читает тело каждого `SKILL.md` на каждый `list`; это ограничение
  публичного контракта, а не кеша. Оптимизация возможна только отдельным решением о смене
  контракта `SkillSummary.body`.
