# Agent Workbench and local code intelligence

## Owners and data flow

- One new managed `packages/services` module owns code-index lifecycle, workspace-scoped local persistence, hybrid search, relationship queries, and index status. UI reads/writes through the existing service hook boundary; UI and renderer never open the database or index files. The Host exposes bounded read-only graph queries to agent runtimes through the existing agent protocol; the CLI never opens the host database directly.
- Index identity is `workspaceIdentity?.trim() || workspacePath`. Database filenames use a stable hash of that identity under the local ZCode data root (`~/.zcode/code-intelligence/`, or the configured data root). Records store normalized workspace-relative paths, file fingerprints and change metadata, parser/index version, symbol/call/dependency edges, text chunks, embedding model identity, and vectors. Credentials, ignored files, and absolute paths are never indexed.
- SQLite is the embedded durable store and lexical/metadata index. Embeddings are stored locally in the same workspace DB. Vector generation supports Ollama's local `/api/embed` response and an OpenAI-compatible `/embeddings` response (including OpenRouter); if no embedding provider is configured, code/symbol/lexical search remains available and the UI reports semantic search as unavailable. No Qdrant service is required for the default install.
- File discovery and parsing are asynchronous and generation-based. The service applies ignore rules from each directory, extracts symbols and import/call edges, embeds changed chunks, then publishes one committed generation. A changed embedding model schedules every indexed chunk for re-embedding; a cancelled or failed generation cannot replace the last usable index. Change detection includes size, mtime, ctime, and the persisted content fingerprint. The first full build remains explicit. When a user starts that build, the Host arms one workspace-scoped native recursive `node:fs.watch` subscription before scanning. Registering the watcher must not recursively enumerate the workspace or wait for a tree-wide readiness crawl; this keeps workspace activation and the initial build from exhausting per-directory watcher resources. Events are filtered to index inputs, coalesced, and trigger incremental refresh; an unknown event path triggers a conservative refresh so changes are not silently missed. Events arriving during a scan or embedding pass mark that workspace dirty and cause one follow-up pass before the shared refresh promise settles. Clearing the index disarms the watcher; Host shutdown closes all watchers. Watch errors remain visible and do not discard the last committed generation. A platform that cannot create a recursive native watcher reports the diagnostic and keeps manual refresh available rather than falling back to a recursive per-directory watcher.
- The Host API is `getStatus`, `indexWorkspace`, `search`, `getSymbolContext`, `getGraphOverview`, `getImpact`, `trace`, `testEmbeddingConfig`, `setEmbeddingConfig`, and `clearIndex`. `indexWorkspace` resolves only after its SQLite transaction commits, including any coalesced follow-up pass; a failure rolls back data and publishes a diagnostic while preserving the previous generation. Watchers are Host-owned and internal to the service. `clearIndex` removes only the database selected by the workspace identity hash and stops its watcher.
- The agent-facing `CodeIndex` provider JSON Schema and runtime parser are generated from the same discriminated action contract; focused contract tests compare every action and exercise the runtime-only workspace-relative path rule. Validation failures return bounded actionable guidance naming the failed field/action without echoing supplied values, source text, credentials, or absolute paths. The normal Read/Grep fallback remains available when a query cannot be corrected.
- The Host owns watcher lifecycle and all index writes. The renderer may submit a draft embedding probe, but that probe must not touch persisted settings or repository content:

- Status is a projection of committed database metadata plus the current in-process indexing operation. It exposes state, generation, timestamps, file/chunk/symbol/edge counts, progress, embedding provider/model/readiness/build phase, whether an API key is saved, and sanitized diagnostics; it never exposes a database path, absolute source path, API key, or source text. Embedding phase distinguishes `not-configured`, `pending`, `building`, `ready`, and `failed`; file-scan progress cannot imply that vector generation is complete. The endpoint is exposed only to the local Model settings form and is omitted from agent protocol status.
- Search accepts a query and bounded result count. It returns relative path, line range, symbol name/kind when known, a short safe excerpt, and whether the match came from lexical or semantic ranking. Semantic ranking is attempted only when an embedding endpoint and model are configured and stored vectors match the complete provider/endpoint/model identity; failures fall back to lexical ranking and appear in diagnostics.
- `setEmbeddingConfig` accepts a provider (`ollama` or `openai-compatible`), endpoint URL, model name, and optional API key, or clears the configuration. Ollama accepts only credential-free loopback HTTP endpoints. OpenAI-compatible providers accept HTTPS, plus credential-free loopback HTTP for local servers. URL query strings, fragments, and embedded username/password are rejected; an API key belongs in the separate token field, never in the URL. Model names are bounded. Omitted fields preserve their current value; explicit `null` clears the whole configuration, while `apiKey: null` clears only the saved key. Saving settings does not make a network call, download, or install a model. The default configuration is unset.
- `testEmbeddingConfig` uses the current draft provider/endpoint/model and an optional transient API key to send one fixed, non-source probe string. It does not save settings, embed repository content, or change the index. The response contains only success, sanitized error category, vector dimensions, and elapsed time; it never includes the probe, endpoint response body, token, or absolute path.
- The endpoint and model/provider identity are persisted in workspace index metadata. The API key is stored only by the Host's `ICredentialService`, using a credential key derived from the hashed workspace identity; it is never persisted in SQLite, returned in status, sent to agent protocol status, or written to logs. The renderer keeps a newly entered key only in transient form state and clears it after save or test. The Host loads the key only when it is about to call the embedding endpoint; an empty key is permitted for local or compatible endpoints that do not require authentication.
- Embedding requests send source chunks during indexing and the search query during semantic search to the configured endpoint. Ollama loopback requests remain on the local machine; an OpenAI-compatible remote endpoint receives those text inputs. The settings UI makes this distinction visible before saving.
- Event order: Workbench submits configuration → Code Intelligence Host validates provider/URL/model → Host saves or deletes the key in `ICredentialService` → Host commits non-secret provider/endpoint/model/key-present metadata in SQLite → status returns only sanitized facts. Testing a draft key is transient and does not save it. After Save, the next probe and a newly created Host load the key from the credential service; a blank token field means keep the saved key. For an embedding request, the Host reads committed settings → loads the workspace key from `ICredentialService` → sends a bounded batch to the selected adapter → validates vectors → stages them → commits the index generation. A failed save/request leaves the previous committed index/configuration usable; no token is copied into index state. Credential writes use the workspace identity hash as the idempotency scope.
- Symbol extraction is TypeScript compiler API based for JS/TS source. Imports create module dependency edges; named declarations are stored with relative source locations. Call edges are best-effort and only emitted when a local declaration can be resolved without guessing. Results mark graph coverage partial when the parser cannot resolve an edge.
- The graph extractor has a persisted parser revision. When it changes, the Host reparses existing source files and atomically rebuilds symbols/import/call facts even when source fingerprints are unchanged. This graph-only migration preserves unchanged chunk text and embedding vectors, and commits the new revision with the rebuilt graph; failure leaves the prior graph generation intact. A regular Refresh does not repeatedly reparse unchanged files after the revision is current.
- Desktop main/host keep the TypeScript compiler API as an external runtime dependency because its CommonJS dynamic `require` cannot be safely inlined into the ESM bundles. Packaged runtime dependency injection and bundle verification must include it.
- GitNexus-style capabilities are implemented behind our own contracts: symbol context, callers/dependencies, impact from changed paths, paths between symbols, and semantic/lexical code query. The full bounded code graph lives in its own Settings section immediately below Usage Stats; Usage Stats remains focused on app and model usage. A compact popover beside the context-window indicator exposes current-workspace index health, search, and the relevant index action; its Open Code Graph action navigates directly to the dedicated section. Advanced relationship queries remain available to the read-only `CodeIndex` agent tool through a strict protocol request scoped to the connected workspace. Query results are bounded and relative-path-only. We do not copy GitNexus source or add it as a runtime dependency.
- `getGraphOverview` returns a bounded connected graph of modules and symbols. The parser emits `contains` edges from a module to its top-level declarations and from each declaration to its direct nested declarations, alongside `calls` and `imports`. Without a focus, the service starts from the highest-degree indexed node and expands through adjacent edges until the node/edge cap is reached; the result is one connected, useful overview slice rather than unrelated popular symbols. With a focus, it returns the selected symbol and its immediate callers/dependencies. It returns stable symbol IDs, names, kinds, workspace-relative paths, line numbers, edge relations, and an explicit partial flag; it never returns source text or absolute paths. SQLite performs the selection and the service does not materialize the full graph in application memory. The GitNexus-inspired ZCode explorer is a graph-only workspace: a compact left filter rail, a dominant pannable/zoomable canvas, and a right symbol inspector, with no chat panel. On wide windows the side rails stay compact (filter rail about 180–220 px; inspector about 260–320 px), leaving at least half the content width for the canvas and fitting the connected slice on first load. The canvas uses a broad, readable layout, restrained symbol-name labels drawn on the nodes, visible connection handles, theme-colored relationship edges, theme-aware controls, and emphasis for selected/focused nodes and their relationship paths. Node-kind and relationship filters only alter the visible bounded slice. All graph UI labels, node-kind names, and accessible node descriptions are localized. On narrow windows, filters and inspector stack around the graph without clipping controls.

## Agent dashboard

- A dedicated Agent Workbench view is the read model for live and recent Swarm runs, named role/profile, attached skills, selected model, child lineage, queue/active capacity, and explicit failure/deadline reasons. Runtime journal/registry and SubagentsService remain authoritative; dashboard does not invent a second mutable run state.
- Embedding configuration is a compact section in Model settings, with provider, endpoint, model, optional token, Test, and Save. Token removal and full reset are secondary actions. Index management and graph exploration are not duplicated there.
- The context-window toolbar includes one compact local-index button. It opens a keyboard-accessible popover for the current workspace, showing state, counts, freshness, embedding readiness, and only the relevant primary action (Build, Refresh, or Retry). Search is available in that popover; the full graph remains in its own Settings section immediately below Usage Stats and low-level impact/trace input forms are not shown as separate dashboard fields.
- The popover never starts an initial full build silently. The first build is user-triggered; after that, Host-owned watch events keep the index current while the workspace is open and reconcile changes made while it was closed. Watchers start when the local workspace becomes active and are also armed before the first build. The graph has explicit empty, partial-coverage, stale, indexing, and failure states; isolated symbols or an edge-empty index never render as a mysterious blank canvas.
- The dashboard is available in Desktop and Web where the host provides the code-intelligence service. Unsupported hosts show an explicit unavailable state and do not attempt local filesystem access.
- The desktop renderer creates the Code Intelligence RPC proxy only for its local Desktop Host connection. Web, mobile replay, and remote workspace transports do not advertise this capability unless their host contract is explicitly extended and reviewed.
- The initial dashboard surface is workspace-scoped and contains profile roster (role, source, enabled state, attached skill names), the current parallel limit and opt-in task time-limit settings, the active task's existing subagent directory projection, local code-index controls/status, and code search. Live run lineage remains read from the existing session subagent projection in its owner conversation; the dashboard embeds that projection and does not duplicate its state.

## Privacy, capacity, and failure

- Default excludes include VCS metadata, dependencies/build outputs, generated bundles/maps, secrets/private keys, and the repository's ignore rules. The service applies size limits and language allowlists before reading content.
- Workspace index data is local and removable per workspace. Workspace removal does not remove agent profiles or task journal data.
- Concurrency is bounded by the user-selected maximum and an adapter-level safe upper bound. `0` means adaptive concurrency, never unlimited uncontrolled file/model fan-out. Spawn count is not a separate root-run budget: the dashboard shows the parallel limit and the opt-in task time limit, and admission rejection reasons come from actual worker-slot capacity (`active_limit`) or the work ledger (`write_claim_conflict`).
- Index/search errors preserve the last committed generation and are visible as diagnostics. Missing embeddings, parser coverage gaps, stale index, and unsupported languages are distinct states.

## Acceptance scenarios

- Workspace identity separates indexes for two remote workspaces that share a display path; local identity falls back to canonical workspace path.
- An incremental refresh updates only changed files and atomically publishes a complete generation; cancellation/failure leaves the last committed index queryable.
- Updating a dependency file preserves inbound imports from unchanged files because module IDs are stable by relative path; outgoing edges for changed files are rebuilt without reloading all indexed chunk text into memory.
- Named calls imported across workspace files resolve to their exported symbol in the local graph; aliases are respected, and unresolved, ambiguous, dynamic, or non-workspace targets remain unlinked instead of being guessed. Modules and declarations are joined by `contains` edges so file-level imports and symbol-level calls can be browsed as one code graph. Re-indexing either the caller or target refreshes the relationship.
- Existing indexes created by an older graph-parser revision backfill imported-call facts on the next index refresh even when source fingerprints match; the backfill does not call the embedding provider or alter vectors for unchanged chunks.
- Ignored, secret-like, over-size, and unsupported files do not enter chunks, graph, or embeddings.
- Lexical and symbol search work without an embedding provider; semantic search uses locally stored vectors when configured and reports model identity.
- Changing the embedding model re-embeds unchanged chunks; saving one embedding field while omitting the other preserves the saved value, while explicit clear removes configuration and vectors.
- The agent `CodeIndex` tool is read-only, can only query the workspace bound to its Host connection, and returns bounded relative paths and excerpts; it is unavailable when the Host does not provide code intelligence.
- For code-repository tasks, any execution-capable role with CodeIndex first checks index status and runs a targeted local search before broad filesystem exploration, then uses context/impact/trace for relationships. Search hits and the focused symbol return the stored chunk for that span, capped at a few kilobytes, plus `endLine`. Related caller, impact, and trace nodes always include `endLine` and include a chunk excerpt only while the response stays inside the existing 24 KB tool cap. Answer from the excerpt and `path:startLine-endLine` when the fact is already in the excerpt. Read only to edit, open a test, or when the excerpt is truncated, `endLine` is missing, or the needed text is absent. Those Reads go out in one parallel batch with `offset = startLine` and a limit covering the range, not the whole file and not every caller. Do not repeat a broad Explore/Grep sweep after the index answered the question. If the service is unavailable, unbuilt, empty, or partial for the requested area, the role says so and falls back to targeted source search. This is not a prohibition on reading source files.
- Before the first model request of a workspace turn, when the index is `ready`, the turn-context owner adds a local lexical/symbol hint for the user text. The hint is a few hits under the same size cap, is not a second source of truth, and does not replace `CodeIndex`. It does not wait on the embedding provider. If the short timeout expires, the turn continues without the hint.
- Child runtimes for the same workspace share the parent's `readFileState` map. The key stays path + mtime + range. Reading the same range again returns the existing stub. A different workspace keeps its own map.
- A successful first build arms the Host watcher. Bursts of file events coalesce into one incremental pass; changes during an active refresh cause a follow-up pass; a failed pass leaves the prior generation searchable and reports stale/degraded status. Watcher scopes follow `workspaceIdentity?.trim() || workspacePath` and are released on index clear or Host shutdown.
- Arming a watcher for a large workspace does not perform a full recursive crawl before `watchWorkspace` returns; nested indexed-file changes and directory renames are detected, ignored-directory events do not schedule index work, and watcher creation failures remain visible without silently switching to a per-directory watcher.
- Same-size edits with a preserved mtime refresh through filesystem change metadata and update the content fingerprint, symbols, edges, chunks, and vectors.
- Nested ignore rules prevent matching files from being read into the index.
- Endpoint configuration rejects disallowed schemes, embedded credentials, URL query/fragment, and invalid model names; a failed embedding request leaves the previous committed generation searchable. Ollama and OpenAI-compatible responses are validated and mapped back to their input order. API keys never appear in status, SQLite records, or diagnostics.
- Model settings can test an Ollama/local or OpenAI-compatible draft endpoint without saving it; the probe sends the same maximum batch size as indexing using fixed non-source strings, so a single-input-only endpoint is caught. A failed probe reports a sanitized, actionable error and never changes existing configuration or vectors. Testing preserves the transient key in the password field so it can be saved after a successful probe.
- Model settings owns embedding configuration: when a local workspace index is available, its provider navigation shows a dedicated Embeddings entry under Workspace intelligence, and the selected detail pane contains the Ollama/OpenAI-compatible endpoint, model, optional API key, test, save, and clear actions. The configuration is scoped to the active local workspace; without a local workspace, the navigation entry is omitted. The Workbench can configure Ollama locally or an OpenAI-compatible endpoint such as `https://openrouter.ai/api/v1/embeddings`, save an optional API key, and clear the key independently; after a successful save, the key is removed from the form and its saved state is indicated without reading the secret back. Empty key input preserves the saved key. Lexical/symbol search continues to work without any model or key.
- The embedding probe classifies HTTP authentication, missing model/route, rate-limit, and provider failures with the HTTP status, while never returning a provider response body, API key, or source content to the UI. Network failures and timeouts remain distinguishable.
- If a bulk embedding build fails after a successful probe, the Code Index popover shows the sanitized batch failure category and HTTP status ahead of partial-coverage warnings. HTTP 429/5xx batches receive at most two bounded retries; lexical indexing stays available, and Refresh retries the build.
- Impact, context, and trace results identify the supporting symbols/files and return an explicit partial result when parser coverage is incomplete.
- Code graph overview and focused neighborhoods return only bounded nodes/edges, use workspace-relative paths, include contains/call/import relation types, and mark results partial when the stored parser coverage or response cap omits graph data. The overview is one connected slice; every selected node beyond the seed has a returned parent edge. The UI retains the last successful graph during refresh/failure, rejects stale responses after workspace/query changes, reloads on generation changes, and keeps empty-index, filtered-empty, loading, and request-failure states distinct.
- The dedicated Code Graph section appears immediately below Usage Stats. It has no chat surface and uses the full Settings content viewport rather than the standard narrow Settings column/card: a compact top toolbar, a compact left filter rail, a dominant full-height pannable/zoomable canvas, and a right inspector. On wide windows the canvas occupies at least half of the content width and initially fits the bounded graph slice, with nodes and focus labels legible at default zoom. The graph canvas must not collapse between side panels or be clipped by a fixed-height card. The graph uses a connected bounded service result laid out as a constellation: symbols that share a directory start in one cluster, then a bounded force pass spreads them so on-node labels and curved edges stay readable at the default fit. Module and file nodes are glowing circles; other symbols are pills colored by kind. Edges are thin theme-colored curves (calls in cyan, imports in magenta, containment subtle) without heavy arrowheads. Hovering a symbol, or choosing one on the canvas, brightens its neighborhood and dims the rest; the first automatic selection does not dim the overview. Incident edges animate unless the user prefers reduced motion. Nodes can be dragged until the next overview reload. Visible connection handles and localized labels remain. All visible graph text, including dynamic node kinds and accessible node descriptions, is localized. On narrow windows the page can scroll and the filter/inspector panels stack around a usable graph canvas.
- Provider fallback notices describe the recorded cause (balance, free usage limit, or long quota wait) and the provider switch. They must not call a provider "unavailable": this runtime fallback is triggered by quota exhaustion, not by a health or connectivity probe.
- Search response `semantic` means a query embedding was successfully produced and vector ranking ran. Each result's `match` field identifies whether that result came from the semantic top-k or lexical retrieval; `semantic: true` does not imply every result is semantic.
- Partial coverage and skipped-file diagnostics are secondary details in a collapsed neutral disclosure. Actual index/provider failures remain visible with semantic error styling; ordinary exclusions and incomplete parser coverage are not shown as alarming banners.
- The context-toolbar dialog keeps the active workspace identity unchanged, does not access SQLite from the renderer, and allows selecting a search result to center its callers and dependencies. Opening it does not trigger an initial build.
- If a graph overview contains no connected symbols, the dialog explains that no local relationships were resolved and still offers indexed search; it does not report the graph as ready with an empty black canvas.
- While the initial index status is unresolved, the graph dashboard shows an explicit loading state and does not present unknown counts as zero. If status loading fails, it stops spinning and offers a retry; a successful retry loads the graph. If the first graph overview request fails after a ready or degraded status, the canvas stops spinning, shows a localized graph error and a Retry action, and loads the graph after a successful retry.
- The bounded overview uses a legible constellation spread for up to 60 symbols, the controls and minimap follow the active theme, and the minimap does not dominate the graph canvas.
- Dashboard rows use the authoritative Swarm run ID and role profile ID; profile edits affect later runs only.
- Removing a workspace index deletes only that workspace's index artifacts.
