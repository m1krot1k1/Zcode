# Публичный набор инструментов модели: Read и Bash без PtySession

## Проблема

В этапе 4.5 `PtySession` был подключён к провайдеру как отдельный инструмент. Одна диагностическая команда превращалась в три последовательных вызова модели: `start` → `write` → `read` (или `wait`). Пользователь видел в транскрипте три карточки `PtySession` подряд и терял время на лишние round-trip.

До этого публичный контракт инструментов состоял из чтения и выполнения команд. Интерактивный PTY нужен терминальным поверхностям и E2E, но не должен менять набор инструментов, который видит модель без явного требования.

## Контракт

- `PtySession` не регистрируется в runtime-наборе инструментов и не попадает в provider-visible список.
- `Read` и `Bash` остаются доступными без изменений; обычная команда выполняется одним вызовом `Bash`.
- PTY-порт и handler сохраняются как внутренняя инфраструктура. `registerBuiltInTools` может зарегистрировать инструмент только при явном `includePtySession: true`; runtime этот флаг не передаёт.
- Никакие новые инструменты или зависимости не добавляются.

## Почему не start/write/read в одном действии

Одноразовый `exec` внутри `PtySession` дублировал бы `Bash` и сохранял бы второй путь выполнения команд. Публичный контракт должен иметь один путь для неинтерактивных команд — `Bash`; интерактивный сценарий остаётся внутренним.

## Приёмка

- `registerBuiltInTools(registry)` регистрирует `Read` и `Bash`, но не `PTY_SESSION_TOOL_NAME`.
- `apps/zcode-cli/packages/core/tests/pty-session-tool.test.ts` покрывает отсутствие инструмента в наборе по умолчанию и сохранение `Read`/`Bash`.
- `apps/zcode-cli/e2e/session-forensic-replay/case-tool-contract.mjs` проверяет перехваченный provider-visible список и одноразовый `Bash`: скрытый `PtySession` получает `Tool not found`, а команда выполняется одним вызовом.
- Handler `PtySession` продолжает работать в тестах при явной передаче порта.
