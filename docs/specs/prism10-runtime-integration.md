## Исполняемый Goal Contract

Переписанное задание, используемое в этой работе:

> На ветке `dev` глубоко проверь текущую историю ZCode и сопоставь реализацию с исходниками PRISM 10.0, OpenCode, Cline, Ouroboros и `.cursor-dev`. Сначала зафиксируй существующие состояния, владельцев, интерфейсы и наблюдаемые сбои; затем обнови эту спецификацию и критерии проверки. Реализуй проверяемые механизмы роя, модели локального OpenCode, MCP и безопасного цикла улучшений внутри текущих границ ZCode. У вложенности не должно быть искусственного предела по глубине; защита от runaway-работы задаётся бюджетом дерева, конкуренцией, проверкой принадлежности и циклов. Сохраняй один авторитетный владелец отмены и событий. Локальный OpenCode CLI с его авторизацией должен быть явно отличим от API-key провайдера OpenCode Go; список моделей и запуск должны использовать установленный/явно устанавливаемый CLI на том Host, где исполняется workspace. Для каждого результата укажи изменённые контракты, тесты и независимо проверяемые receipts; не называй prompt, план, локальный gate или PR доказательством успешного результата LLM. Создавай коммиты на русском и отправляй только в `dev`; не мержи в `main`. Подтверди публикацию по фактическому GitHub Release и файлам, иначе точно укажи блокирующее ограничение.

## Контракт локального macOS release gate

Локальный выпуск должен до изменения версии и сборки подтвердить доступную Developer ID Application signing identity и ровно один полный набор credential variables для notarization. Затем electron-builder v26 подписывает и нотариализует production `.app`, stapling ticket; локальный app gate и SHA/asset проверки остаются обязательными до `git push` и `gh release create`.

1. Собрать ровно DMG и ZIP для версии из `package.json` и архитектуры текущего Mac. Проверить имена и SHA-256 локальных файлов; не выбирать preview/test/другую архитектуру.
2. Проверить именно `.app`, созданный этой сборкой и вложенный в release artifacts: `codesign --verify --deep --strict` и локальная оценка Gatekeeper `spctl -a -vv -t exec`. Нельзя подменять проверку собранного app проверкой иной уже установленной копии.
3. Проверить stapled notarization главного `.app` через `xcrun stapler validate`. Существующий `scripts/doctor-macos-release-app.sh` всегда проверяет подпись/Gatekeeper главного app, но stapled ticket проверяет только для отдельного Computer Use Helper при `ZCODE_CUA_REQUIRE_HELPER=1`. Поэтому release gate должен явно включить проверку ticket главного app; одной проверки `spctl` недостаточно, поскольку Gatekeeper может получить ticket из сети или кэша.
4. До изменения `package.json` и запуска сборки проверить в выбранном macOS keychain (по умолчанию или `CSC_KEYCHAIN`) валидную signing identity с префиксом `Developer ID Application:`. Для notarization принять ровно один комплект: `APPLE_API_KEY` + `APPLE_API_KEY_ID` + `APPLE_API_ISSUER`; либо `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID`; либо `APPLE_KEYCHAIN_PROFILE` (с `APPLE_KEYCHAIN` только если указан). Не печатать значения credential variables. Сборка release явно включает `ZCODE_ENABLE_MAC_SIGN=1` и `ZCODE_ENABLE_MAC_NOTARIZE=1`; конфигурация включает `forceCodeSigning`, `hardenedRuntime` и `mac.notarize`. Обычные dev/preview builds без этих флагов не требуют Apple credentials и не запускают signing/notarization.
5. Если preflight не нашёл Developer ID identity или полный набор notarization credentials, завершиться до изменения версии/сборки. Локальный preflight проверяет доступность identity и полноту переменных, но не может доказать, что Apple примет credentials без реального notarization запроса; фактический build gate должен остановить продвижение при отказе подписи или notarization до commit/push.
6. После подготовки commit версии зафиксировать ожидаемый `releaseCommitSha`. Отправить именно этот commit в `dev` и до создания релиза подтвердить, что удалённый `dev` указывает на тот же SHA. Передать этот SHA как точную цель создания tag/release; после создания прочитать GitHub tag ref и подтвердить, что он разрешается в тот же commit. Сам факт `gh release create --target dev` без проверки разрешённого tag SHA недостаточен.
7. После публикации проверить draft/tag, ровно ожидаемую пару asset names и SHA-256 каждого скачанного GitHub asset против локальной пары. Зелёный unit test этих сравнений не заменяет фактическую проверку GitHub.

Контракт подписания/notarization сверяется с официальной [electron-builder v26 MacConfiguration](https://www.electron.build/v26/docs/api/app-builder-lib.interface.macconfiguration/), [v26 macOS Notarization](https://www.electron.build/v26/docs/notarization/) и [v26 Code Signing](https://www.electron.build/v26/docs/features/code-signing/). Документация указывает Developer ID Application для прямого распространения, `forceCodeSigning` для отказа при отсутствии подписи, credential sets выше и автоматический staple при `mac.notarize: true`.

## Владельцы и границы

```text
Root runtime / Host
  ├─ goal run id, root budget, generation и общий task registry
  ├─ Task DAG ─ dependency/ready/admission ─> Agent tree (parent/child ownership)
  ├─ append-only session events ─> terminal lifecycle projection; future AC receipts
  ├─ stop(root/node) ─> abort descendants ─> дождаться settlement ─> terminal lifecycle event
  └─ Host external-agent service ─> OpenCode CLI resolver/installer/ACP process на том же Host

Renderer: черновик и команды через сервисный контракт; не владеет очередью/процессом.
```

- Agent tree задаёт владельца и каскад отмены. Task DAG задаёт зависимости и готовность. Успешное завершение сообщения не означает завершение внешнего действия.
- Общий registry не заменяется локальными картами в child runtime. Cancellation handle регистрируется до того, как родитель может ждать readiness; abort во время startup всегда закрывает readiness gate.
- Успешно завершившийся parent turn может оставить явно background child работать. Уничтожение/перезапуск parent runtime отменяет его потомков через один cascade owner. Остановка одного узла не отменяет соседнюю ветвь.
- Отмена фиксируется в порядке: принять запрос → единый владелец закрывает session owners и передаёт abort всему target subtree → дождаться фактического settlement → опубликовать terminal snapshot и удерживать admission/terminal waiters до завершения артефактов, уведомлений и событий финализатора. При таком cascade дочерний `closeBrowserSession` видит уже закрытого owner и не запускает повторный обход/ожидание descendants; верхний владелец остаётся единственным settlement barrier. Самостоятельное закрытие дочерней сессии по-прежнему отменяет и дожидается её собственных детей. Повторный запуск того же task id ждёт завершения финализатора; cancel возвращает snapshot остановленного lifecycle. Любой event старого run generation отбрасывается.
- Ни одна установка, OAuth-сессия, ключ или право не наследуются только на основании наличия parent-child связи. Ребёнок получает подмножество полномочий родителя.
- Local OpenCode CLI обнаруживается/запускается Host-ом, исполняющим target workspace (включая remote/WSL). Renderer и Desktop Main не читают хранилище auth CLI. `opencode acp` использует ACP JSON-RPC через stdio; его совместимость подтверждается реальным `initialize`, а не наличием `--stdio` в `opencode serve --help`. ACP process запускается без shell-интерполяции, ограничен workspace cwd, имеет явные permissions/consent, преобразует протокольные события в ZCode session events и закрывается вместе с владельцем.

## Поведение роя

- Agent tree не имеет cumulative лимита числа узлов и не имеет предела глубины. Admission отклоняет только закрытого/остановленного владельца, конфликт lineage/реальный цикл или исчерпанную root-session active-work quota. Ограничение размера одной декларации Task DAG не ограничивает рекурсивные Agent вызовы между узлами.
- Root-session concurrency остаётся ограниченной 24 одновременно исполняемыми leaf-work items, включая разные coordinator turns/root runs, поскольку background child может пережить turn запуска. Foreground-вложение передаёт слот от ожидающего родителя дочернему runtime; background child расходует слот отдельно. Admission проверяет projected count до регистрации, а foreground → background отклоняется без изменения состояния, если переход превысит квоту. Per-task inactivity watchdog, abort cascade и owner/cycle fencing остаются независимыми ограничителями.
- Terminal RuntimeTask snapshots остаются доступны в пределах жизни root runtime: они нужны `TaskOutput`, `SubagentPort.getTask`/`waitForTask`, сообщениям завершившейся задаче и PRISM terminal projection. После settlement completed Agent snapshot сохраняет статус, acceptance/usage и output-file path, но освобождает содержимое результата и исходный prompt; `TaskOutput` перечитывает полный результат из output file. Это ограничивает тяжёлые поля на одну запись, но количество compact snapshots всё ещё растёт с количеством выполненных задач и не является строгим total-memory budget. Cancellation handles и finalization markers освобождаются после settlement; terminal metadata сохраняется для текущих consumers.
- Идентификатор child идемпотентен в рамках запроса; parent обязан принадлежать тому же root run; запрет циклического повторного присоединения lineage; прекращённый root не принимает spawn/resume; stale generation не может мутировать новую ветку.
- Жизненный цикл задачи единолично хранит root-scoped `RuntimeTaskRegistry`. Новый `subagent_execution_terminal` event строится из committed terminal snapshot и передаётся через существующий `AgentRuntime.appendEvent` в `SessionEventStorePort`; его проекция также append-only сохраняется как `SessionEntryInfo` в root session через тот же `SessionStorePort`. Отдельной очереди или дублирующего реестра нет. Payload связывает `rootRunId`, `taskId`, `attemptId`, необязательный `parentTaskId`, `branchGeneration`, `childSessionId` и стабильный `terminalId`, вычисляемый с включением `attemptId`; повторное использование task ID создаёт отдельную terminal запись. Event store envelope задаёт собственные event id/sequence/timestamp.
- Это append-only terminal lifecycle projection, а не execution/evidence receipt: provenance равен `runtime_lifecycle`, `acceptanceStatus` отражает только сохранённый Host acceptance. Если отмена произошла до запуска child runtime, наружный `terminalStatus` равен `cancelled`, даже когда внутренний Registry хранит `killed` как технический статус остановленного запуска. Event не подтверждает выполнение claim, качество результата или прохождение AC; `SubagentStopped(completed)` и LLM GoalCompletionVerification также не являются независимой проверкой.
- Payload lifecycle event ограничен lineage, terminal status, provenance и временем наблюдения; он не содержит prompt, output, error, raw logs, env или credentials и не участвует в acceptance.
- Task contract и evidence receipt хранятся как типизированные `SessionEntryInfo` в существующем `SessionStorePort`, с корневой сессией как единственным durable владельцем; отдельный реестр/очередь и SQL migration не вводятся. Contract ограничен 16 критериями и 500 UTF-8 байтами на описание. Receipt привязан к `rootRunId`, `taskId`, `attemptId`, `criterionId`, `branchGeneration`, хешу контракта и версии evaluator; полный payload не превышает 32 KiB.
- Только Host-side evaluator с фиксированной версией может записать `pass`; worker/LLM receipt остаётся `untrusted` и никогда не повышает acceptance. Детерминированная свёртка принимает результат лишь при полном совпадении lineage, попытки, текущего поколения ветки и SHA-256 контракта, а также наличии отдельного проверяемого artifact SHA-256. Завершение задачи без таких receipts остаётся `unknown`.
- Записи append-only и идемпотентны по stable receipt id: повтор с тем же payload безопасен, конфликтующий повтор отклоняется. Если store не поддерживает запись или persistence не удалась, verified/accepted не возвращается; cold resume перечитывает записи из того же store.
- Contract schema, receipt validation, pure reducer и root-session persistence path внедрены. Receipt child session обязана совпадать с дочерней сессией текущей записи Registry; terminal projection также проверяет актуальную attempt lineage, сохраняется в root session и допускает только идентичный повтор stable terminal id. Одновременные записи одного terminal id сериализуются внутри единственного session owner; межпроцессный compare-and-set не реализован, потому что все события одной сессии маршрутизируются через её owner runtime. Конфликтный payload не может перезаписать первый снимок. Для contract/evidence/terminal событий сначала завершается durable validation и запись, и только затем событие добавляется в replay event store; отклонённое или несохранённое событие не становится replay-фактом. Root-session SessionEntry является авторитетным durable фактом PRISM; event store/live sinks — последующие проекции. Если проекция падает после durable commit, вызывающая сторона получает успех, чтобы сохранённый receipt не исключался из acceptance, а warning помечает деградацию; такой event может отсутствовать в live/replay памяти, автоматической outbox-переигровки пока нет. Ошибка проверки или durable save по-прежнему отклоняет событие до event store. Текущий ограниченный PRISM-01 slice объявляет contract до запуска child, принимает только Host-side receipt с точной lineage, artifact hash и зафиксированной evaluator version; доступный production evaluator подтверждает лишь результат точной Bash-команды, не семантическую корректность цели или изменения. Историческая acceptance-проекция доступна после cold resume только для завершённых попыток; активные runtime-задачи и процессы не восстанавливаются. Semantic evaluator, возобновление исполняемых задач и end-to-end подтверждение качества роя остаются незавершёнными; синтетические receipts не доказывают их. Task DAG v1 реализуется и проверяется по критериям ниже.
- Глобальные quota не снимают provider throttling. На 429 сохранять статус провайдера/Retry-After и показывать пользователю; никакой автоматической смены аккаунта/ключа или ротации для обхода лимита.

### PRISM Task DAG v1

`Agent` получает необязательный `task_graph: { nodes, max_parallel? }` — bounded список узлов с уникальными ID, описанием, prompt, списком `depends_on`, необязательным типом агента и узловыми acceptance criteria. `max_parallel` имеет диапазон 1–24 и default 8. Один вызов задаёт общий objective (`description`/`prompt`) и исполняет план foreground; `run_in_background` и общие criteria на весь DAG при этом запрещены, чтобы не смешивать два владельца результата.

Граф полностью валидируется до первого запуска: не более 128 узлов, `max_parallel` от 1 до 24, только существующие уникальные зависимости, без self-edge и циклов, а также уникальные ID acceptance criteria внутри каждого узла. Лимит 120 000 байт измеряется по UTF-8 сериализованному нормализованному JSON всего графа с именами полей и структурными символами. Это ограничивает только форму одной декларации Task DAG и не ограничивает число или глубину runtime Agent nodes. Root-scoped registry применяет общую квоту 24 активных leaf-work items ко всем потомкам и конкурентным вызовам; per-task watchdog и закрытие owner остаются дополнительными ресурсными границами. Aggregate token/time quota для последовательных задач пока не реализована и не подразумевается.

Узлы запускаются через существующий `SubagentPort.run` и остаются обычными child runtime в единственном `RuntimeTaskRegistry`; план/ready-set временно принадлежит текущему вызову root runtime и не копируется в Renderer или отдельную persisted очередь. Ready означает, что все непосредственные зависимости завершились `completed` и ни у одной нет явного Host acceptance `rejected`. `unknown` acceptance не блокирует порядок выполнения и всегда явно отражается в отчёте: запуск потомка не объявляет цель или артефакт доказанными. Вывод зависимости передаётся как явно размеченные недоверенные данные; downstream агенту запрещено выполнять или принимать инструкции внутри этого текста. Чтобы prerequisite не раздувал prompt, в контекст одного зависимого узла попадает не более 24 KiB суммарного JSON с ответами и не более 4 KiB на один prerequisite; длинный ответ усекается, а пропущенная часть явно обозначается. Ошибка, отмена или Host rejection блокирует только потомков этого узла; независимые ready-ветви продолжаются. Повторное terminal событие не может второй раз разблокировать узел, потому что scheduler наблюдает единственное завершение Promise конкретного запуска.

Отмена родительского tool call прекращает запуск pending узлов, передаёт тот же abort signal всем работающим children и ждёт их реального settlement через существующий lifecycle; после отмены нет запуска новых descendants. Итог одного `Agent` tool call перечисляет каждый узел, фактический terminal status, Host acceptance и доступный результат. Сводный UTF-8 результат ограничен 64 KiB; длинные описания и ответы узлов усекаются с явной отметкой, чтобы размер tool output оставался ограниченным даже для большого графа. Статус завершения самого wrapper означает только, что scheduler остановился, а не что весь objective принят. План не восстанавливается после холодного перезапуска; активные runtime-задачи также не восстанавливаются, а сохранённые terminal/receipt записи остаются read-only историей.

## OpenCode provider contract

- В Settings видны разные способы доступа:
  - `OpenCode CLI` — делегированный agent runtime с локальной авторизацией OpenCode, API key не нужен; состояние установки/версии и каталог моделей берутся из ACP capabilities/config options CLI процесса. В UI явно показано, что OpenCode владеет инструментами текущего запуска.
- `OpenCode API` — hosted endpoint, пользователю нужен API key. Никакой вид/текст UI не должен обещать локальную авторизацию для него.
- API provider catalog содержит один видимый OpenCode entry с общей API-key авторизацией и объединёнными моделями Go/Zen. Для каждой исходной записи сохраняется точный wire protocol и base URL (`/zen/go/v1` либо `/zen/v1`); одинаковые model ID представлены единожды: если хотя бы один исходный маршрут включён, выбирается включённый маршрут, при равенстве приоритет у Go, а при отсутствии включённых маршрутов запись остаётся выключенной. Протокол/URL задаются явно на уровне модели; неизвестный protocol не получает опасный fallback на Chat Completions. Local CLI не участвует в API `Model` adapter, поскольку OpenCode server выполняет собственный agent loop и инструменты.
- `opencode-go` из committed baseline и шесть дополнительных прежних Go/Zen template IDs остаются во внутренней карте как deprecated compatibility entries с исходными API endpoint/protocol/model rules, но не выдаются в список создания и не принимаются при создании новых provider instances. Уже сохранённые providers продолжают разрешаться без переписывания ключей, endpoint или выбранных моделей; Settings показывает только единый новый OpenCode entry.
- Local CLI UX: обнаружить в PATH и поддерживаемых платформенных путях; ручной путь; проверить version/handshake; показать ясные состояния `not installed`, `login required`, `ready`, `unsupported version`, `failed`. Явная кнопка install использует проверяемый официальный дистрибутив/OS package manager, показывает версию, не выполняет произвольный shell из каталога MCP и не меняет OAuth/key store.
- При обновлении модели пользователь выбирает её через текущую ZCode model selection service; выбранный ID сохраняется вместе с provider identity. Секреты CLI не экспортируются в ZCode provider config.

## MCP и цикл улучшений

- Cline import добавляет source discovery и parser для подтверждённых settings formats; сохраняет transport-specific config и enabled state. Переносит только совместимую OAuth client registration; не копирует access/refresh tokens, verifier или Cline auth state — ZCode начинает собственную OAuth авторизацию. В Global/user scope env, headers и OAuth client secret сохраняются только в существующем private config contract (файл с правами `0600`). В Project/workspace scope эти значения не записываются: сохраняются несекретные параметры, а результат каждого такого импорта явно предупреждает, что секретные значения пропущены, без раскрытия значений. Одна лишь предварительная заметка не разрешает проектное сохранение секретов. Ошибки/конфликты остаются явными, существующие данные не перезаписываются.
- MCP catalog в первой итерации является встроенным, неизменяемым, вручную курируемым списком metadata (имя, provenance, пакет/транспорт, auth requirement), а не удалённым marketplace feed. Выбор готовит черновик существующей формы; сохранение и handshake идут через текущий MCP settings owner. До явного Save ничего не записывается и сервер не запускается. API key остаётся пустым полем для пользователя. OAuth-backed Cline endpoints не показываются как installable presets, пока не подтверждён отдельный ZCode OAuth contract.
- В проверенном Cline профиле десять записей: пять существующих stdio пресетов уже доступны в каталоге; добавлен официальный Firecrawl stdio пакет `firecrawl-mcp@3.33.0`, версия закреплена по upstream `server.json`. Черновик содержит пустой `FIRECRAWL_API_KEY` и видимую пометку: ключ не обязателен для keyless tier, нужен для account features. Browserbase, Todoist, Webflow и Apify остаются импортируемыми пользовательскими конфигурациями, но не one-click пресетами до проверки их auth/OAuth контракта. Сохранённые Cline OAuth/token state не переносятся.
- Safe EVO-01 local preflight проверяет явно staged candidate diff, но не выполняет promotion. JSONL receipts используют `schema=zcode.prism.receipt.v2`; допустимые `criterion_id` и точные команды заданы в repo-owned allowlist. В этом slice единственный критерий `SELF-IMPROVE-HELPER-TESTS` разрешает точную команду `node --test scripts/test/self-improve-pr.test.mjs`. Любой staged rename/copy отклоняется до подготовки PR; остальные staged пути извлекаются через NUL-delimited diff без rename detection и проверяются по секретным именам. `artifact_path` разрешается относительно каталога evidence файла, должен указывать на обычный файл внутри этого каталога и ограничен 10 MiB. Helper повторно читает байты и вычисляет SHA-256; указанный `artifact_sha256` принимается только при совпадении с пересчитанным hash. URL не принимаются. Критерий, команда и локальный artifact остаются self-reported: это `VALIDATED_LOCAL`, не подтверждение запуска команды, provenance, независимой оценки или качества изменения.
- Receipt v2 — strict JSONL shape: только `schema`, `criterion_id`, `reported_status`, `command`, `exit_code`, `observed_at`, `base_sha`, `candidate_patch_sha256`, `artifact_path`, `artifact_sha256`; неизвестные поля, недостающие/дублированные criteria и неподтверждённые команды отклоняются.
- CLI default mode печатает только локальный план. Явный `--apply` ограничен созданием отдельной ветки, commit на русском, push и открытием **Draft PR** в `dev`; auto-merge, promotion и release запрещены. PR содержит только allowlisted criterion ID и пересчитанный artifact hash, не раскрывает локальные пути и явно называет доказательства неподтверждёнными.
- Для полного EVO-01 локальные Node integration tests используют временный Git repository и injectable fake `git`/`gh` write runner, проверяют отказ до недопустимых side effects и Draft параметры; test запускается отдельной командой и включён в `verify:pre-push`. Это проверяет процедуру локально без GitHub credentials, но не подтверждает GitHub workflow identity. Следующий внешний шаг — CI-attested receipt, привязанный к точному PR SHA, защищённый evaluator/holdout и отдельное reviewed решение о promotion/rollback. Изменение evaluator, system permissions или holdout не может задним числом улучшать собственный score.

## Реализация и критерии приёмки

### Актуализация PRISM task lifecycle (2026-10-21)

Первый production evaluator ограничен проверкой фактически выполненной Bash-команды с точным текстом и exit code `0`. Agent tool принимает явные `acceptance_criteria` только этого типа; Host отображает их на фиксированный `evaluatorId/version`, объявляет контракт после admission и до child runtime, затем сопоставляет criteria с `ToolCallScheduled` и отдельным структурированным Host-свидетельством `ToolCallResult`. В контракт записывается команда как criterion input; в событии результата — только SHA-256 команды, process status и exit code. LLM-текст и worker receipts не участвуют в решении.

В persisted-контракте хранится только SHA-256 точной команды; raw command существует только во входе Agent и дочернем `ToolCallScheduled`. Результат принимается, только если его session/turn/toolCallId совпадают с последней подходящей постановкой и `result.sequenceNumber > scheduled.sequenceNumber`. Это исключает повторное использование прежнего ToolCallResult при повторе той же команды с тем же ID.

Каждый receipt содержит ограниченный самодостаточный snapshot проверяемого Bash evidence (IDs и sequence исходных событий, hash команды, завершённый статус и exit code), его canonical SHA-256 и source URI. URI служит для трассировки, но replay проверки не зависит от живого in-memory event store. Receipt ID связывает lineage, решение и hash artifact; persisted reducer повторно проверяет hash/размер snapshot и его соответствие критерию контракта. Exit code `0` даёт `pass`; ненулевой код даёт `fail`; отсутствующее, неоднозначное, предшествующее постановке, фоновое или неполное событие не создаёт receipt и оставляет решение `unknown`. Критерий `verified` доказывает только выполнение указанного процесса с указанным кодом; он не доказывает качество патча, безопасность, корректность теста или выполнение естественно-языковой цели. Задача без явных machine-verifiable критериев остаётся `unknown`.

Событие терминала попытки содержит фактический Host acceptance status для completed output; фоновые уведомления показывают тот же статус. Если admission отменён после durable contract declaration, lifecycle всё равно записывает terminal state `cancelled` с acceptance `unknown`. Setup, завершившийся до declaration, не создаёт PRISM-контракт.

Cold resume не восстанавливает PRISM-узлы как текущие registry-задачи. Историческая read-only acceptance-проекция прикрепляется только к уже существующей строке завершённого child в `session/subagents`; `snapshot.subagents`, `ResumeSessionResult`, активная очередь и task registry не становятся вторым хранилищем истории. Источник проекции — root-session `SessionEntry`; она вычисляется заново при чтении каталога и не записывается обратно, не создаёт lifecycle events и не запускает процесс.

Статус выдаётся только когда active-branch transcript однозначно связывает строку с `childSessionId`, task/tool-call ID и root run; для direct child run привязан к turn ID вызова, для nested child наследуется через единственный terminal непосредственного родителя. Для точной попытки должны совпасть durable leaf contract, terminal, receipts, stable entry IDs, `taskType=subagent_child`, `SessionInfo.parentID`, `parentTaskId` и вся цепочка terminal-владельцев до runtime root; родительскому task не требуется собственный PRISM contract или критерии, но каждый его terminal обязан описывать завершённое создание child. У каждого звена проверяется актуальный `branchGeneration` непосредственного owner session и отсутствие циклов/разрывов. Повреждённая дублирующая terminal запись для той же пары task/child, неверный `childStarted` или неоднозначный terminal запрещают `verified`. Затем существующий reducer пересчитывает решение, а сохранённый `terminal.acceptanceStatus` принимается только при точном совпадении. Если PRISM-запись относится к child, но terminal/owner/родительская цепочка/attempt неоднозначны, отсутствуют или устарели, поле показывает `unknown`. Не-PRISM child не получает нового поля. Contract без terminal (например, процесс завершился аварийно) остаётся `unknown` и не оживляет RuntimeTaskRegistry, AgentRuntime или фоновую работу. История для одной страницы directory индексируется одним проходом по root-session entries и активным transcript; дальнейшая проверка использует точные ключи task/child/attempt и не повторно сканирует всю историю для каждой строки. Если одна child session связана с несколькими попытками и их нельзя отличить по transcript, не выбирать последнюю эвристически: показывать `unknown`. Сводка не раскрывает command, artifact snapshot или receipt URI; она никогда не означает, что естественно-языковая цель выполнена. Внешний/self-improvement evaluator, защищённый holdout и release promotion остаются отдельной работой.

### Cline MCP import diagnostics (2026-10-21)

Обнаруженный дефект: JSON parse errors и записи Cline, не прошедшие нормализацию, сводятся к пустой карте. UI не отличает «источник отсутствует» от «источник есть, но повреждён», а частично валидный файл импортируется без сообщения о пропусках. Исправление добавляет машинно-читаемые причины `invalidConfig`, `invalidEntries` и `unreadable` на уровень категории источника. Сохраняются валидные записи; диагностические данные не включают содержимое ошибки или секреты. Критерий MCP-03: fixture с невалидным JSON/формой показывает диагностическое состояние, fixture с одной валидной и одной невалидной записью сохраняет валидную запись и сообщает точное количество пропусков, а сериализованные результаты не содержат тестовых секретов.

В исходниках нет системного сценария с формулировкой «проверю статус патчей». `package.json` и `pnpm-lock.yaml` содержат шесть активных pnpm patched dependencies для сторонних пакетов; удалять их нельзя на основании скриншота. Проверка `git fetch`/freshness — отдельный baseline workflow, а не runtime patch requirement. Node 26/pnpm 11 предупреждает, что игнорирует `patchedDependencies`; для сборки необходим закреплённый Node 24/pnpm 10.

Статический анализ/юнит-тест не доказывает работающий GUI и реальный provider login. Для UI нужен accepted E2E сценарий; для проверки OpenCode model auth требуется отдельный реальный модельный прогон на пользовательском CLI; текущий ACP handshake выполнялся на локальном CLI с изолированными XDG data/config, без создания durable session и без model request. Для GitHub Release требуется удалённый tag, target SHA и загруженные asset hashes.

### Реальная вложенная AgentRuntime и каскад остановки (2026-10-21)

Реестрный тест с фиктивными cancellation handles подтверждает только lineage/admission; тесты `subagent-tool-events` покрывают один реальный runtime child. Для регрессии runtime ownership добавлен критерий PRISM-02: корневой `AgentRuntime` запускает child, тот запускает grandchild через тот же root-scoped registry; остановка root должна передать abort всему дереву и оставаться pending до фактического завершения grandchild. Проверка требует точный внутренний terminal status `killed` и соответствующий terminal payload для обоих уже запущенных потомков, плюс две durable записи в root `SessionStore`. Это доказывает каскад на конечном дереве из трёх уровней, но само по себе не доказывает отсутствие искусственного depth guard, холодное восстановление процессов или наличие Task DAG scheduler.

Admission не подменяет nesting cap другим cumulative node count: root-session active-work quota остаётся конечной; foreground-вложение заменяет ожидающего родителя в счётчике, background child учитывается отдельно. Aggregate tokens/time на root run сейчас не представлены отдельным admission ledger, поэтому нельзя утверждать, что concurrency ограничивает суммарный расход длинной последовательной цепочки. После финализации Agent registry сохраняет compact terminal state и ссылку на output file; `TaskOutput` читает текст с диска. Количество compact snapshots ограничено только сроком жизни root runtime, поэтому это сокращает удержание тяжёлых строк, но не обещает математически bounded total memory/work. Teardown ждёт потомков и освобождает registry вместе с владельцем.

Проверка реальной цепочки глубже 24 пока не закрыта: ограниченный AgentRuntime прогон на 25 узлов не достиг leaf; по истечении 45 секунд registry содержал 23 задачи на глубине 23, было 23 model requests, `backgrounded=0`, все задачи оставались `running`. Прогон завершился до root close и turn settlement, поэтому не устанавливает причину stall. Отдельная попытка цепочки из 129 runtime уровней завершилась OOM и также не подтверждает рабочую глубину. Эти результаты — незакрытые проверки; не заявлять production-поддержку глубины выше 23 до диагностики и успешного bounded runtime evidence.

### Диагностика глубокой цепочки и границ готовности (2026-10-21)

В коде не найден отдельный depth guard. Root concurrency quota 24 не объясняет остановку линейной foreground-цепочки: ожидающий родитель передаёт свой слот ребёнку. Наблюдение цепочки на глубине 23 не содержит stage telemetry и потому не устанавливает причину.

Source trace выявил два дефекта маршрутизации: уже помеченный `source="subagent"` mirror мог повторно идти в ancestor sinks; raw event descendant также зеркалировался каждым предком с чужим `agentId`/`childSessionId`. Mirror должен оставаться проекцией своего непосредственного parent и не передаваться выше повторно. Raw event продолжает подниматься как raw; runtime создаёт mirror только когда `event.sessionId` совпадает с session ID его непосредственного child. Первый OOM-прогон тестовой цепочки был ошибочным: fake model создавал новый Agent при каждом follow-up запросе и строил ветвление вместо линейной цепочки, поэтому OOM не доказывал дефект production runtime. После исправления mock-а реальная цепочка из 25 вложенных child завершилась, а тест закрепляет правильный direct-child owner, отсутствие повторного mirror и heap ниже 1.5 GiB.

Регрессия доказывается bounded интеграционным тестом реальных `AgentRuntime` с линейной вложенностью больше `SUBAGENT_ROOT_MAX_ACTIVE_TASKS`. Один запуск записывает по каждому `childSessionId` task admission, последнюю lifecycle event и вызовы model factory; успех требует завершения всех child и предков. Timeout только ограничивает тест и включает самый глубокий узел и последний этап каждого активного узла. Production sink/store не подменяется тестовым timeout.

Если будущая цепочка остановится на одном этапе, исправлять только подтверждённого владельца этого ожидания, сохраняя порядок durable event → notification → model request. Deadline не является production recovery или доказательством причины. Synthetic registry chain, рост RSS/OOM либо успешный ACP handshake без model request не доказывают реальную runtime-глубину. Отдельно остаются root-scoped cumulative resource accounting и ограниченное хранение terminal snapshots без возврата искусственного depth/node cap.

## Источники сравнения и выбор решений

- Ouroboros: брать разделение discovery, task intake, agent-tree coordination и verifier/evidence; не копировать самостоятельный harness вместо Host/runtime ZCode.
- `.cursor-dev`: брать делегирование по независимым задачам, explicit owner/AC и сбор результатов; не использовать внутренние cursor patch scripts как ZCode интеграцию.
- Cline: брать явное разделение local CLI auth и API-key provider и UI каталога моделей; Cline SDK фактически вызывает OpenCode `session.prompt`, где OpenCode владеет своим tool loop. Переносится такое разделение ownership, а не маскировка делегированного агента под чистый LLM adapter. Текущий diff добавляет явный импорт пользовательских MCP settings; этот путь не является каталогом/marketplace.
