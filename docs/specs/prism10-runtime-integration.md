## Исполняемый Goal Contract

Переписанное задание, используемое в этой работе:

> На ветке `dev` глубоко проверь текущую историю ZCode и сопоставь реализацию с исходниками PRISM 10.0, OpenCode, Cline, Ouroboros и `.cursor-dev`. Сначала зафиксируй существующие состояния, владельцев, интерфейсы и наблюдаемые сбои; затем обнови эту спецификацию и критерии проверки. Реализуй проверяемые механизмы роя, модели локального OpenCode, MCP и безопасного цикла улучшений внутри текущих границ ZCode. У вложенности не должно быть искусственного предела по глубине; защита от runaway-работы задаётся бюджетом дерева, конкуренцией, проверкой принадлежности и циклов. Сохраняй один авторитетный владелец отмены и событий. Локальный OpenCode CLI с его авторизацией должен быть явно отличим от API-key провайдера OpenCode Go; список моделей и запуск должны использовать установленный/явно устанавливаемый CLI на том Host, где исполняется workspace. Не обходи ответы 429 и не читай/копируй секреты OpenCode. Исправь подтверждённые дефекты Cline MCP import, добавь безопасный каталог MCP, усили проверки локального macOS-релиза. Для каждого результата укажи изменённые контракты, тесты и независимо проверяемые receipts; не называй prompt, план, локальный gate или PR доказательством успешного результата LLM. Создавай коммиты на русском и отправляй только в `dev`; не мержи в `main`. Подтверди публикацию по фактическому GitHub Release и файлам, иначе точно укажи блокирующее ограничение.

## Контракт локального macOS release gate

Локальный выпуск должен до изменения версии и сборки подтвердить доступную Developer ID Application signing identity и ровно один полный набор credential variables для notarization. Затем electron-builder v26 подписывает и нотариализует production `.app`, stapling ticket; локальный app gate и SHA/asset проверки остаются обязательными до `git push` и `gh release create`.

1. Собрать ровно DMG и ZIP для версии из `package.json` и архитектуры текущего Mac. Проверить имена и SHA-256 локальных файлов; не выбирать preview/test/другую архитектуру.
2. Проверить именно `.app`, созданный этой сборкой и вложенный в release artifacts: `codesign --verify --deep --strict` и локальная оценка Gatekeeper `spctl -a -vv -t exec`. Нельзя подменять проверку собранного app проверкой иной уже установленной копии.
3. Проверить stapled notarization главного `.app` через `xcrun stapler validate`. Существующий `scripts/doctor-macos-release-app.sh` всегда проверяет подпись/Gatekeeper главного app, но stapled ticket проверяет только для отдельного Computer Use Helper при `ZCODE_CUA_REQUIRE_HELPER=1`. Поэтому release gate должен явно включить проверку ticket главного app; одной проверки `spctl` недостаточно, поскольку Gatekeeper может получить ticket из сети или кэша.
4. До изменения `package.json` и запуска сборки проверить в выбранном macOS keychain (по умолчанию или `CSC_KEYCHAIN`) валидную signing identity с префиксом `Developer ID Application:`. Для notarization принять ровно один комплект: `APPLE_API_KEY` + `APPLE_API_KEY_ID` + `APPLE_API_ISSUER`; либо `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID`; либо `APPLE_KEYCHAIN_PROFILE` (с `APPLE_KEYCHAIN` только если указан). Не печатать значения credential variables. Сборка release явно включает `ZCODE_ENABLE_MAC_SIGN=1` и `ZCODE_ENABLE_MAC_NOTARIZE=1`; конфигурация включает `forceCodeSigning`, `hardenedRuntime` и `mac.notarize`. Обычные dev/preview builds без этих флагов не требуют Apple credentials и не запускают signing/notarization.
5. Если preflight не нашёл Developer ID identity или полный набор notarization credentials, завершиться до изменения версии/сборки. Локальный preflight проверяет доступность identity и полноту переменных, но не может доказать, что Apple примет credentials без реального notarization запроса; фактический build gate должен остановить продвижение при отказе подписи или notarization до commit/push.
6. После подготовки commit версии зафиксировать ожидаемый `releaseCommitSha`. Отправить именно этот commit в `dev` и до создания релиза подтвердить, что удалённый `dev` указывает на тот же SHA. Передать этот SHA как точную цель создания tag/release; после создания прочитать GitHub tag ref и подтвердить, что он разрешается в тот же commit. Сам факт `gh release create --target dev` без проверки разрешённого tag SHA недостаточен.
7. После публикации проверить draft/tag, ровно ожидаемую пару asset names и SHA-256 каждого скачанного GitHub asset против локальной пары. Зелёный unit test этих сравнений не заменяет фактическую проверку GitHub.

Контракт подписания/notarization сверяется с официальной [electron-builder v26 MacConfiguration](https://www.electron.build/v26/docs/api/app-builder-lib.interface.macconfiguration/), [v26 macOS Notarization](https://www.electron.build/v26/docs/notarization/) и [v26 Code Signing](https://www.electron.build/v26/docs/features/code-signing/). Документация указывает Developer ID Application для прямого распространения, `forceCodeSigning` для отказа при отсутствии подписи, credential sets выше и автоматический staple при `mac.notarize: true`.

Для проверки без реальной публикации разрешён только инъецируемый fake command runner/API: сценарий должен пройти локальные gates, передать точный commit SHA и asset set в план и остановиться перед любым реальным `push`/`gh release create`. Отдельные negative cases обязаны остановиться при подписи/notarization rejection и tag SHA mismatch.

## Владельцы и границы

```text
Root runtime / Host
  ├─ goal run id, root budget, generation и общий task registry
  ├─ Task DAG ─ dependency/ready/admission ─> Agent tree (parent/child ownership)
  ├─ append-only session events ─> terminal lifecycle projection; future AC receipts
  ├─ stop(root/node) ─> abort descendants ─> дождаться settlement ─> terminal lifecycle event
  └─ Host external-agent service ─> OpenCode CLI resolver/installer/ACP process на том же Host

Renderer: черновик и команды через сервисный контракт; не владеет очередью/процессом.
```

- Agent tree задаёт владельца и каскад отмены. Task DAG задаёт зависимости и готовность. Успешное завершение сообщения не означает завершение внешнего действия.
- Общий registry не заменяется локальными картами в child runtime. Cancellation handle регистрируется до того, как родитель может ждать readiness; abort во время startup всегда закрывает readiness gate.
- Успешно завершившийся parent turn может оставить явно background child работать. Уничтожение/перезапуск parent runtime отменяет его прямых потомков; каждый потомок делает то же для собственных. Остановка одного узла не отменяет соседнюю ветвь.
- Отмена фиксируется в порядке: принять запрос → передать abort всему target subtree → дождаться фактического settlement → опубликовать terminal snapshot и удерживать admission/terminal waiters до завершения артефактов, уведомлений и событий финализатора. Повторный запуск того же task id ждёт завершения финализатора; cancel возвращает snapshot остановленного lifecycle. Любой event старого run generation отбрасывается.
- Ни одна установка, OAuth-сессия, ключ или право не наследуются только на основании наличия parent-child связи. Ребёнок получает подмножество полномочий родителя.
- Local OpenCode CLI обнаруживается/запускается Host-ом, исполняющим target workspace (включая remote/WSL). Renderer и Desktop Main не читают хранилище auth CLI. ACP process запускается без shell-интерполяции, ограничен workspace cwd, имеет явные permissions/consent, преобразует протокольные события в ZCode session events и закрывается вместе с владельцем.

## Поведение роя

- Удалить `DEFAULT_MAX_SUBAGENT_DEPTH`, `ABSOLUTE_MAX_SUBAGENT_DEPTH`, `ZCODE_MAX_SUBAGENT_DEPTH` и persisted depth denial. Дочерняя задача может порождать задачи любой глубины, пока root run открыт и admission допускает её.
- Первоначальные runtime quotas: максимум 128 узлов на root run и 24 одновременно активных узла на весь root session, включая разные coordinator turns/root runs, поскольку background child может пережить turn запуска. Проверка должна учитывать новый узел до регистрации: `existing < max`; попытка сверх бюджета возвращает типизированный отказ без создания child session. Значения должны быть единым root-owned policy, наблюдаемыми и тестируемыми, а не размноженными локальными константами.
- Идентификатор child идемпотентен в рамках запроса; parent обязан принадлежать тому же root run; запрет циклического повторного присоединения lineage; прекращённый root не принимает spawn/resume; stale generation не может мутировать новую ветку.
- Жизненный цикл задачи единолично хранит root-scoped `RuntimeTaskRegistry`. Новый `subagent_execution_terminal` event строится из committed terminal snapshot и передаётся через существующий `AgentRuntime.appendEvent` в `SessionEventStorePort`; отдельной очереди или дублирующего реестра нет. Payload связывает `rootRunId`, `taskId`, необязательный `parentTaskId`, `branchGeneration`, `childSessionId` и стабильный `terminalId`; event store envelope задаёт собственные event id/sequence/timestamp.
- Это append-only terminal lifecycle projection, а не execution/evidence receipt: provenance равен `runtime_lifecycle`, `terminalStatus` копирует терминальный статус Registry, а `acceptanceStatus` всегда `unknown`. Event не подтверждает выполнение claim, качество результата или прохождение AC; `SubagentStopped(completed)` и LLM GoalCompletionVerification также не являются независимой проверкой.
- Payload ограничен идентификаторами lineage, terminal status, schema/provenance и временем наблюдения; он не содержит prompt, output, error, raw logs, env или credentials. Будущий criterion-specific receipt требует сначала структурированных критериев и отдельного Host-side observer/evaluator с версией и ограниченной ссылкой/хешем артефакта. Такая проверка пока не реализована, PRISM-01 остаётся unmet.
- Глобальные quota не снимают provider throttling. На 429 сохранять статус провайдера/Retry-After и показывать пользователю; никакой автоматической смены аккаунта/ключа или ротации для обхода лимита.

## OpenCode provider contract

- В Settings видны разные способы доступа:
  - `OpenCode CLI` — делегированный agent runtime с локальной авторизацией OpenCode, API key не нужен; состояние установки/версии и каталог моделей берутся из ACP capabilities/config options CLI процесса. В UI явно показано, что OpenCode владеет инструментами текущего запуска.
  - `OpenCode Go` — hosted endpoint, пользователю нужен API key. Никакой вид/текст UI не должен обещать локальную авторизацию для него.
- API provider catalog содержит один OpenCode Go entry. Для каждой модели используется корректный wire protocol из проверенной метаинформации; неизвестный protocol не получает опасный fallback на Chat Completions. Local CLI не участвует в API `Model` adapter, поскольку OpenCode server выполняет собственный agent loop и инструменты.
- Local CLI UX: обнаружить в PATH и поддерживаемых платформенных путях; ручной путь; проверить version/handshake; показать ясные состояния `not installed`, `login required`, `ready`, `unsupported version`, `failed`. Явная кнопка install использует проверяемый официальный дистрибутив/OS package manager, показывает версию, не выполняет произвольный shell из каталога MCP и не меняет OAuth/key store.
- При обновлении модели пользователь выбирает её через текущую ZCode model selection service; выбранный ID сохраняется вместе с provider identity. Секреты CLI не экспортируются в ZCode provider config.

## MCP и цикл улучшений

- Cline import добавляет source discovery и parser для подтверждённых settings formats; сохраняет transport-specific config и enabled state. Переносит только совместимую OAuth client registration; не копирует access/refresh tokens, verifier или Cline auth state — ZCode начинает собственную OAuth авторизацию. В Global/user scope env, headers и OAuth client secret сохраняются только в существующем private config contract (файл с правами `0600`). В Project/workspace scope эти значения не записываются: сохраняются несекретные параметры, а результат каждого такого импорта явно предупреждает, что секретные значения пропущены, без раскрытия значений. Одна лишь предварительная заметка не разрешает проектное сохранение секретов. Ошибки/конфликты остаются явными, существующие данные не перезаписываются.
- MCP catalog — opt-in metadata с транспортом, командой/URL, параметрами авторизации и происхождением. Установка использует текущий MCP settings owner; до запуска/подтверждения не исполняет remote code. Источник и запись marketplace — разные сущности.
- Self-improvement workflow создаёт isolated branch/PR только из явно staged candidate diff. Candidate receipts имеют формат JSONL: `schema=zcode.prism.receipt.v1`, `criterion_id`, `status=pass`, `command`, `exit_code=0`, `observed_at`, `base_sha`, `candidate_patch_sha256`, `artifact_url` и `artifact_sha256`. PR helper проверяет структуру receipts, HTTPS-ссылку и соответствие hash базовому revision и staged patch; он не удостоверяет содержимое artifacts или независимость оценки. Полная оценка дополнительно хранит baseline/candidate configuration, фиксированный grader/version, неизменённый holdout identity, budget, negative/regression results и rollback commit/revision. До внешних независимых результатов status не выше `VALIDATED_LOCAL`.
- Изменение evaluator, system permissions или holdout — отдельный reviewed change и не может задним числом улучшать собственный score. PR автоматически не мержится и не публикуется как release.

В исходниках нет системного сценария с формулировкой «проверю статус патчей». `package.json` и `pnpm-lock.yaml` содержат шесть активных pnpm patched dependencies для сторонних пакетов; удалять их нельзя на основании скриншота. Проверка `git fetch`/freshness — отдельный baseline workflow, а не runtime patch requirement. Node 26/pnpm 11 предупреждает, что игнорирует `patchedDependencies`; для сборки необходим закреплённый Node 24/pnpm 10.

Статический анализ/юнит-тест не доказывает работающий GUI и реальный provider login. Для UI нужен accepted E2E сценарий; для OpenCode требуется реальный ACP handshake и реальный модельный прогон на доступном CLI; для GitHub Release требуется удалённый tag, target SHA и загруженные asset hashes.

## Источники сравнения и выбор решений

- Ouroboros: брать разделение discovery, task intake, agent-tree coordination и verifier/evidence; не копировать самостоятельный harness вместо Host/runtime ZCode.
- `.cursor-dev`: брать делегирование по независимым задачам, explicit owner/AC и сбор результатов; не использовать внутренние cursor patch scripts как ZCode интеграцию.
- Cline: брать явное разделение local CLI auth и API-key provider и UI каталога моделей; Cline SDK фактически вызывает OpenCode `session.prompt`, где OpenCode владеет своим tool loop. Переносится такое разделение ownership, а не маскировка делегированного агента под чистый LLM adapter. Текущий diff добавляет явный импорт пользовательских MCP settings; этот путь не является каталогом/marketplace.
- OpenCode: использовать официальный локальный CLI/ACP protocol и auth lifecycle вместо чтения `auth.json` или подмены ключей.
- ZCode: сохранять Host ownership, существующий Provider Registry, MCP settings, session event order, workspace identity, Windows/macOS/Linux абстракции и release scopes.

## Ограничения проверки

- `node scripts/check-workspace-freshness.mjs` сейчас не может выполнить `git fetch`: `.git/FETCH_HEAD` недоступен для записи в sandbox. Существующий `origin/dev` ref остаётся локальным снимком, пока fetch не прошёл.
- В session отсутствуют Node 24.14.0/pnpm 10.33.2 из `mise.toml`; доступный fallback — Node 26.9.0/pnpm 11.25.0, который игнорирует `pnpm.patchedDependencies`; архитектурная команда прервала попытку bootstrap/install без TTY. Не считать такую установку или сборку валидной.
- Текущий тестовый `.app` `packages/desktop/dist/mac-arm64/ZCode Preview.app` отклонён локальными `codesign --verify --deep --strict` и `spctl -a -vv -t exec`; `xcrun stapler validate` не обнаружил notarization ticket. Это подтверждает, что данный артефакт не проходит release contract, но не является приёмкой новой production-сборки.
- Реальная production-сборка не запускалась: unit tests проверяют parsing/наличие identity и полноту credential variables, но не подтверждают Apple acceptance credentials. Проверка `xcrun stapler validate` подтверждает staple уже собранного приложения, а не успешность будущего нотариального запроса.
- GitHub CLI авторизация и GitHub connector пока не подтверждают доступ к приватному `m1krot1k1/Zcode`; push и публикацию нельзя считать выполненными до получения внешнего ответа.
