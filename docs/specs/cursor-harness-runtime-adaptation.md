# ZCode native agent runtime

## Goal

ZCode owns and ships its agent roles, rules, skills, delegation behavior, and result delivery. Research from neighboring harnesses, including `../.cursor-dev`, informed this contract only; a downloaded ZCode build must not depend on those repositories or on Cursor being installed.

This is ZCode's product contract, not a copy of another editor's host implementation. Host-only Python hooks, binary patches, machine-specific model settings, and external MCP configuration are not portable runtime behavior. ZCode's typed commands, hooks, MCP, skills, session persistence, permissions, and desktop streaming remain their owners.

## Evidence-backed source inventory

The source research covered 11 named agents, 16 `.mdc` rules, 82 skill directories in the sibling `.cursor-dev` source, slash commands, host hooks, a state/wave format, and evaluation cases. ZCode owns its adapted role roster, exact-profile dispatch, bundled rule/skill pack, inherited context snapshots, bounded Swarm DAG, and child-session previews. Packaged builds do not read neighboring repositories at runtime and remain self-contained. The source inventory is a capability audit, not an instruction to copy every directory: each portable capability must either have a verified ZCode owner or an explicit, reasoned exclusion. A similar name or a neighboring repo-only skill does not count as a product-runtime equivalent.

Current Desktop E2E evidence proves that ordinary Composer Swarm requests create two child sessions, show each child's partial and complete output, and render root synthesis in the originating chat. This proves in-process execution and live preview only. `SwarmRunUpdated`, the node scheduler state, and `RuntimeTaskRegistry` are currently process-local; the CLI session store persists accepted input and transcripts but not a validated Swarm graph or node attempts. Durable restart-resume remains unimplemented. Its future owner is the ZCode CLI session store/SQLite (`db.sqlite`), with Core as the sole transition/admission/scheduling owner; the required CAS, `ownerEpoch`, child-session side-effect, and interrupted-attempt contract is specified in [the Swarm mode spec](zcode-swarm-mode.md). The bundled pack now includes ZCode-native research, domain modeling, UI craft, merge-conflict resolution, handoff, measured performance tuning, and MCP authoring procedures. User profile CRUD already belongs to Settings → Subagents and the ZCode profile roots; in-place updates now use atomic replacement, while coordinated recovery for a rename interrupted between writing the new profile and deleting the old one remains open. Other product/runtime gaps remain: an evidence-gated durable lesson capture path; a reusable evaluation-case owner beyond individual E2E specs; and coordinated profile-rename recovery. The full source disposition is tracked in [the native harness capability map](zcode-native-harness-capability-map.md). These gaps must be handled through existing ZCode owners or new ZCode-owned contracts before this adaptation can be called functionally complete. Host-specific hooks, patches, unsafe refusal/jailbreak overrides, unlimited/exponential fan-out, fixed external model routing, and machine-local external wave files are not transferred.

## Product contract

### Named agents

- The active built-in ZCode roster is `start`, `orchestrator`, `researcher`, `implementer`, `reviewer`, `security-reviewer`, `test-engineer`, `evaluator`, `self-improver`, `knowledge-curator`, and `subagent-factory`. Normal `Agent`/`Task` calls also see separately configured custom profiles. Swarm uses an immutable snapshot of only these 11 canonical built-ins for planner, admission, and every Swarm descendant.
- Agent selection is always explicit by exact active profile ID. `Agent` and `Task` are aliases for the same typed dispatch; neither has a built-in `general`/`general-purpose` role or silently defaults to one. Unknown/missing IDs fail before child-session creation and return the available names. Custom profiles must be explicitly authored in ZCode's user/project/plugin configuration; Cursor workspace files are not runtime inputs.
- Swarm planning and normal Agent/Task dispatch share the same 11 canonical built-in ZCode roles listed above, plus explicitly configured ZCode custom profiles where the caller allows them. The planner may select only the 11 canonical built-ins. Generic compatibility profiles and `Explore` are never advertised as fallback roles. A custom profile may not shadow a canonical Swarm role; Swarm uses the canonical built-in role contract.
- A role is a profile contract: concise purpose, scoped system prompt, explicit tools, and an allowlist of ZCode-packaged skills. `start`/`orchestrator`/eligible specialists may delegate only when their profile and every ancestor allow it. Read-only roles remain read-only by runtime tool allowlist, not by prompt alone.
- A missing or empty skill allowlist grants no skill access. A child's `Skill` tool is exposed only when at least one skill is explicitly allowed, and runtime filtering enforces the same rule even for a fabricated tool call.
- The bootstrap profile parser accepts only ZCode-owned document metadata (`path`, `source`, optional ZCode `namespace`, and content). It has no source-host format discriminator or Cursor-specific precedence; only `.zcode/agents` and ZCode user/plugin roots are valid profile inputs.
- A selected Swarm plan must use named active roles. It may not invent a `general` role to recover from a provider's suggested name.
- `start` uses a compact intake envelope before routing: outcome, constraints/scope, user-authorized work, and only blocking unknowns. It does not ask for approval already given, invent a saved mission, or claim restart-resume behavior that the runtime does not own.
- `orchestrator` gives each branch a bounded mission envelope with owner/profile, deliverable, disjoint scope, dependencies, and evidence required at join. It delegates only genuinely independent work, keeps fan-out within runtime budgets, and does not recursively expand a single capability probe into duplicate trees. Join checks the user-requested deliverables against source/test evidence and names any incomplete item.
- `self-improver` starts from an observed failure and one testable mechanism, records evidence/mechanism/hypothesis/check/rollback, runs the same check before and after the narrow reversible change, and retains it only if the predicted delta appears. If the check cannot run, it reports that limitation; it does not claim measured improvement. It does not create durable lessons or edit its own prompt without an explicit owner and evidence. ZCode task/session snapshots are not a persisted mission-wave/resume store; no automatic continuation after process restart is claimed.

### Rules and skills

- Runtime loads bundled ZCode-adapted harness rules plus native `.zcode/rules/*.mdc` through the single `NodeContextSourceAdapter` context-source owner. Cursor-specific workspace folders are not read by the runtime. The bundled pack is `apps/zcode-cli/packages/bundled-skills/rules/`; it ships beside the CLI in Desktop, remote hosts, and is included in the SEA content-hash manifest. Every deployment validator must check the same required rule and skill inventory so a partial pack cannot be advertised as complete. No absolute install path or sibling `.cursor-dev` lookup is allowed.
- The root conversation follows the ZCode `start` role gateway contract by default: answer-only and trivial requests stay in the root turn; actionable, non-trivial workspace tasks dispatch the visible `Task(start)` tool before workspace tools, and `start` either returns a direct result or delegates to `orchestrator`. This is a normal root-turn tool call with a visible child session, not a hidden preflight planner or an implicit `general-purpose` fallback. Interactive root sessions and eligible descendants expose the typed `Task` alias with exact-profile validation. The model still selects whether a request is actionable; the runtime guarantees the tool is available and validates the selected profile, while tool allowlists remain authoritative. If the active runtime cannot expose the named `start` role, it must surface that limitation and preserve the ordinary direct chat path.
- `/start`, `/review`, `/evolve`, and `/evaluate` are first-party, protocol-visible ZCode prompt commands. They are registered by ZCode's shared slash-command catalog and expand through the existing command path in Desktop and CLI; the packaged runtime never looks beside the application for `.cursor-dev`. Each command names the corresponding exact role (`start`, `reviewer`, `self-improver`, or `evaluator`), carries its bounded output contract and allowed skills, and never authorizes a tool or permission that the runtime did not provide.
- `/review` requires an independent reviewer and read-only review; it does not let the reviewer edit the reviewed change. `/evolve` starts only from a named, observable failure and keeps safety/verification gates immutable. `/evaluate` reports individual pass/fail/not-run evidence and cannot turn missing evidence into a pass. `/start` routes trivial requests directly and non-trivial work through the named gateway. These commands remain ordinary ZCode turns and retain normal model choice, cancellation, streaming, permissions, and session history.
- Keep a source-to-native capability inventory for all discovered source agents, rules, skill entrypoints, hooks, commands, state, and evaluation cases. Each item is marked `native`, `adapt`, `reuse-plugin`, or `exclude` and names its ZCode owner or the reason it cannot be transferred. Marking only related prose as `native` is insufficient when the source feature includes persistence, admission, UI, or verification behavior.
- Adapt every portable harness procedure that is in the product scope into a ZCode-owned bundled skill, plugin skill, typed command, permission/admission contract, persistence owner, or E2E case. Reuse the existing owner when equivalent; do not create a second subsystem. Skill text must name only tools and UI that ZCode actually provides. Domain catalogues may remain optional plugin packs, but every source skill must have an explicit disposition in the inventory rather than silently disappearing from a curated subset. Current bundle and plugin inventory is recorded in [the native harness capability map](zcode-native-harness-capability-map.md) and must stay synchronized with packaging.
- The capability inventory does not authorize copying unsafe or host-bound behavior. Do not transfer refusal/jailbreak overrides, host binary patches, shell hooks that bypass admission, fixed external model routing, machine-specific paths/credentials, or external state files. Any replacement must preserve ZCode user authorization, safety, permissions, cancellation, and product APIs.
- The canonical root `ContextSourceSnapshot` owns separate immutable `bundledHarnessRules` and `workspaceRules` arrays. The root resolves both once; every descendant receives those same accepted arrays through `subagentContext` and does not resolve a second, potentially different copy. Bundled rules are always-on and workspace rules retain existing `alwaysApply`/concrete-target `globs` behavior.
- This same snapshot contract applies to normal `Task`/`Agent` descendants and workflow-created children (`createWorkflowFacade` and script-workflow child runtime). A workflow child must receive the root's accepted arrays and resolved bundled-resource root through its existing typed context dependency; it must not construct a fresh default adapter or re-read mutable workspace rules. This must hold for Desktop, remote Host, and SEA layouts.
- The supported frontmatter is `description`, `alwaysApply`, and `globs`; malformed metadata and unsafe paths yield diagnostics and are not applied. Bundled rules are packaged constants and must be valid, always-on rules.
- The bundled set adapts evidence, delegation, verification, context, model identity, code/UI craft, and forward progress. It deliberately excludes source-harness jailbreak/refusal rules, machine/host patches, and any instruction that attempts to alter safety, authority, permissions, or runtime policy.
- Bundled rules and `alwaysApply: true` workspace rules are included in every root and child agent context. A `globs` rule applies only when a concrete workspace-relative target path is known to match; the runtime must not infer a target from vague prompt text. All rendered rule content remains untrusted meta-user guidance and cannot change permission mode, tool allowlists, trust, system instructions, or runtime validation.
- Skills remain on-demand `Skill` tool resources. Their descriptions are discoverable in the profile's inherited allowlist; full skill bodies are loaded only by calling `Skill`, and every descendant intersects its skill access with every ancestor. Workflow-created child runtimes receive the same bundled skill root as the root runtime, with only `dynamic-workflows` removed because those children cannot launch workflows. Bundled skills must be present in Desktop and SEA packages; no runtime lookup of the sibling `.cursor-dev` is allowed.
- Test-driven development is a ZCode-owned, always-bundled skill available to implementer and test-engineer profiles. It follows repository specs and public test seams, adds a focused regression test for behavior changes, and reports only checks actually run. It has no dependency on an optional skill plugin or sibling repository.
- ZCode-owned built-ins are always available from its packaged profile and skill/rule inventories. Native user/project inputs come from `.zcode/agents`, `.zcode/skills`, and `.zcode/rules`; `.cursor` folders are ignored so stale host-specific prompts cannot inject incompatible role names or tool assumptions. The shipped runtime and built-in pack must work with empty HOME and must not require the Cursor application, `.cursor-dev`, or any adjacent repository.
- Curate harness skills by function and reuse existing ZCode skills where equivalent. Do not bulk-copy domain-specific or host-patching skills. Translate Cursor commands/hooks/state/evals to existing ZCode commands, trusted typed hooks, task/session persistence, and E2E case catalogs instead of adding a second parallel subsystem.

### Delegation and visible results

- Each child receives an explicit role, task envelope, inherited accepted workspace-rule snapshot, allowed skills/tools, cancellation signal, and parent/root lineage. Child role, tool, and skill permissions can only narrow down the tree.
- The root runtime owns plan admission and DAG execution; the task registry owns in-process child lifecycle and lineage; process-local session events feed live UI previews; the UI renders live child text from those sessions. The CLI session store owns durable accepted input and transcripts, but currently owns no restartable Swarm run/node state. Do not treat session events, transcript inference, Host task-index projections, or the in-memory registry as a recovery journal; do not synthesize child transcripts into the root history.
- A running Swarm row must expose ready child IDs, exact named roles, status, and each child's live assistant text before the DAG completes. Root synthesis is a separate subsequent message. Planner `leaf`, refusal, parse/transport failure, or timeout before spawn must continue as a normal direct turn without a red error or a stuck spinner. Errors after child admission remain visible.

### Durable mission state disposition

- Current disposition: bounded in-turn DAG execution and live child previews are ZCode-owned; durable Swarm restart-resume is a tracked capability gap. The source harness's `waves.json`, scripts, and automatic continuation are excluded and must not be read or written by ZCode.
- Future acceptance requires a typed journal in the CLI session store/SQLite. Core alone chooses transitions; adapter calls persist them with revision CAS and `ownerEpoch` fencing. Accepted `sourceCommandId` and stable run/node/attempt identities make retries idempotent. Child-session creation/linkage must commit idempotently before model execution; after a restart, unsafe `dispatching`/`running` attempts are reconciled and marked `interrupted`, never blindly redispatched. See the normative event and acceptance contract in [the Swarm mode spec](zcode-swarm-mode.md).

## Ownership and event order

```text
Composer send (explicit role intent / Swarm toggle)
  -> CLI canonical input intent
  -> Core AgentRuntime resolves one ContextSourceSnapshot and profile snapshot
      -> NodeContextSourceAdapter loads AGENTS.md + bundled harness rules + applicable workspace rule files
      -> Agent/Task validates exact profile + inherited tool/skill envelope
      -> SubagentPort / DAG runner admits child and records parent/root lineage
      -> Task/Agent child AgentRuntime reuses same accepted context/rule snapshot and filtered tools/skills
      -> workflow facade/script workflow creates a child with the same snapshot and bundled-resource root
      -> SessionEventStore streams child assistant events
      -> SwarmRunUpdated publishes only ready child session IDs and named roles
  -> UI subscribes to child sessions and displays live previews while root is running
  -> Core joins child outputs, starts root synthesis, and emits normal completion
```

The root accepted snapshot is immutable for the turn and is reused by descendants. In particular, `bundledHarnessRules` and `workspaceRules` are resolved once and passed into each child context; children do not read a later disk state. Desktop continuous delivery and web-remote replayable delivery remain separate; this specification's live-preview assertion is for the Desktop conversation surface unless the replayable path has a separately accepted case.

## Implementation sequence

1. Keep the Swarm/profile specs and case catalog aligned with the current named-role and live-output contracts.
2. Preserve exact-profile dispatch and the curated role catalog; cover any regression back to an implicit generic fallback.
3. Preserve the bundled rule/context snapshot and root/child inheritance contracts.
4. Keep the curated skill inventory consistent across Desktop/SEA/remote bundles.
5. Pass OpenCode skill requests through the current runtime's filtered `SkillPort`, and preserve the accepted context snapshot in workflow-created descendants.
6. Promote focused runtime and Desktop E2E cases, then inspect a build from the current source and observe live child output before calling those cases complete.
7. Register and test the four ZCode built-in gateway/review/evolution/evaluation commands through the existing ZCode slash-command surface; keep command names reserved and package all referenced skills.
8. Verify the default root gateway behavior with both an answer-only request and a real named Task dispatch; prompt text or a static profile list alone is not evidence that runtime routing works.

Local unit tests and bundle string checks are not evidence of a running Desktop E2E. Do not close a case until its named runtime or UI assertion has been observed.
