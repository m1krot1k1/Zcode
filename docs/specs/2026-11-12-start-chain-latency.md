# Скорость /start и цепочки агентов

Статус: реализовано в `dev` (2026-11-12).

## Зачем

`/start` — не нативная команда, а подстановка промпта: корневой агент обязан вызвать
`Task(start)`, `start` — ровно один `Task(orchestrator)`, оркестратор — исполнителей.
Цепочка сохраняется по продуктовому требованию: пользователь запускает `/start`, дальше
работает оркестратор и его агенты, включая вложенное делегирование.

До изменения каждый переход стоил одинаково дорого:

- подсказка указателя кода добавлялась всем ролям, включая `start`/`orchestrator`,
  у которых единственный инструмент — `Task`: до 2 секунд ожидания Host и до 12 КБ
  контекста на переход, применить которые нечем;
- каталог навыков до 20 КБ добавлялся ролям без инструмента `Skill`;
- исполнителям предписывалось начинать с `CodeIndex status` → `search` даже когда
  подсказка уже лежала в контексте;
- при переполнении worker-слотов admission сразу возвращал `active_limit`, и модель
  тратила ещё один полный запрос (7–25 с), чтобы повторить `Task`; в графе задач ветка
  сразу помечалась `failed`.

## Контракт

1. `injectCodeIndexTurnHint` выполняется только если у runtime есть `Read` или
   `CodeIndex` (`hasCodeReadingTools`). Router-роли подсказку не получают.
2. Каталог навыков в контексте субагента показывается только при наличии `Skill` или
   `SkillSearch` (`hasSkillTools`).
3. Профильный контракт исполнителей: если `code-index hint` уже в контексте — не
   вызывать `status/search` повторно; иначе порядок «status → адресный search» сохраняется.
4. `RuntimeTaskRegistry.waitForCapacityChange({ signal })` будит ожидающих при
   освобождении слота (терминальный переход, снятие running-задачи, удаление).
   `registerSubagentTaskWithCapacityWait` ждёт слот до 10 минут с шагом 1 секунда и
   уважает отмену родителя; по истечении срока возвращается прежний отказ `active_limit`.
5. `model.request.completed` содержит `agentType` и `sessionId`, чтобы один trace
   раскладывался по переходам без догадок.

## Инварианты

- Цепочка `root → start → orchestrator → workers` не меняется.
- Ожидание слота не создаёт вторую очередь и не обходит `RuntimeTaskRegistry`:
  единственный владелец задач и отмены остаётся прежним.
- Отмена родителя прерывает ожидание и возвращает штатный отказ; новые ветки не стартуют.
- Подсказка указателя кода не является вторым источником истины и не заменяет `CodeIndex`.

## Router-модель

`agents-state.json → builtInModelSelectionOverrides` теперь принимает `start` и
`orchestrator`: если Host/настройки задали для них модель, `normalizeAgentProfiles`
применяет её как профильную, а worker-роли продолжают наследовать модель сессии.
В настройках субагентов у этих ролей появился выбор модели. Без override поведение
прежнее — маршрутизаторы идут на модели пользователя.

Миграция `agents-state.json` сохраняет router-ключи (раньше выбрасывала всё, кроме
`Explore`/`general-purpose`).

## Что осталось за рамками
