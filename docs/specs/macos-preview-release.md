# macOS Preview prerelease without Apple signing credentials

## Product contract

An explicitly requested macOS Preview prerelease may be built on a developer's Mac and published to the existing GitHub repository without Developer ID or notarization credentials. It uses the isolated `ZCode Preview` identity, bundle ID `dev.zcode.app.preview`, and a valid space-free Preview executable name; the `.app` display name remains `ZCode Preview`. Build-time bundle and `app.asar` paths must derive from the same platform executable identity that electron-builder uses (`ZCodePreview.app` for Preview), while Finder display name and release artifact names retain `ZCode Preview`.

Preview bundles are ad-hoc signed, not Developer ID-signed and not notarized. electron-builder runs with `mac.identity: null` for this build (the Preview build environment sets `ZCODE_ENABLE_MAC_SIGN=0`, `ZCODE_ENABLE_MAC_NOTARIZE=0`, and `CSC_IDENTITY_AUTO_DISCOVERY=false` and removes `APPLE_*`/`CSC_*` variables); no Apple signing credential is used or required, and the hook only checks those variables for presence so it can stay disabled. Because electron-builder does not sign a bundle when the identity is null, the Preview `afterPack` hook runs `codesign --force --deep --sign -` on the packaged `.app` after `app.asar` and runtime resources are finalized and before `packageInDistributableFormat` creates the DMG/ZIP. The hook is disabled for non-macOS and non-Preview builds, when signing is enabled or `forceCodeSigning` is set, and when `APPLE_SIGNING_IDENTITY`, `CSC_NAME`, `CSC_LINK`, or `CSC_KEYCHAIN` is present. Signing is idempotent and succeeds only when `codesign --verify --deep --strict` passes, `codesign -dv --verbose=2` reports `Signature=adhoc`, the bundle seals its resources (`Sealed Resources version=` present), which distinguishes a real bundle signature from Electron's linker-signed executable, and every nested `.app` under the bundle's `Contents/` passes `codesign --verify --strict`. The nested check is required because `codesign --deep` does not seal `.app` bundles located in `Contents/Resources` while the root `--deep --verify` still exits 0; `applyMacAdHocSignature` signs each discovered nested bundle explicitly before signing the root, and recursively walks real directories only, without following symlinks, so Electron framework `Versions/Current` links and cycles are skipped. Nested discovery is fail-closed and contained: an unreadable or unresolvable directory aborts signing with an error naming that path instead of being skipped, and `Contents` plus every traversed real directory must resolve inside the real path of the target `.app`, so a `Contents` symlink or nested path escaping the bundle fails the gate instead of signing a bundle outside it. Release preflight sets `requireAdHocSignature` and applies the same check to the source `.app` and to the app extracted from both ZIP and DMG; the extracted bundles must also match the source tree hash, so the three copies carry one consistent bundle and signature. The preflight app directory follows electron-builder's `defaultArch` layout (`dist/mac-arm64` for arm64, `dist/mac` for x64).

This Preview is an offline ZCode-service build. It does not require an account or a test backend. Every compiled ZCode backend origin used by Desktop main, Host, services, and renderer resolves to `http://127.0.0.1:0`, an unavailable loopback endpoint. Offline Preview must also avoid automatic or user-triggered requests to ZCode-owned production CDNs: the official catalog and its assets may be shown from an existing local cache or bundled data, but refreshes and downloads that require `cdn-zcode.z.ai` or `cdn.codegeex.cn/zcode` are unavailable. Built-in plugins and explicitly configured personal marketplace sources keep their existing behavior. ZCode-owned CDN images use a local fallback rather than making an image request. Account-dependent Rewards navigation is disabled in this build so it cannot open the public ZCode site. ZCode telemetry and automatic update checks are disabled. This does not disable user-configured external model providers or the local OpenCode CLI provider. Preview release notes must say that ZCode account/backend and official-CDN-dependent features are unavailable in this build; the endpoint can be configured later when the user's own service exists. Shell and `.env` values must not redirect this build to a public ZCode origin. The GitHub assets must carry the `_TEST` suffix, be marked as a prerelease, and state clearly that Gatekeeper may block first launch until the user approves it. It must never be represented as a Developer ID-signed or notarized production release or overwrite the stable release channel.

While GitHub Actions billing is unavailable, the cross-platform workflow is manual-only; this local macOS Preview script is the canonical release path. Windows/Linux installers remain unavailable until billing is restored.

Before building, the release script verifies that the active Node version exactly matches the `[tools] node` pin in `mise.toml` (currently 24.14.0). On mismatch it stops before any build or publication step, names the actual and pinned versions, and tells the user to run `mise exec -- pnpm release:macos:preview <major|minor|patch>` (or `mise exec -- pnpm release:macos <major|minor|patch>`).

## Release owner and sequence

The local release script owns version bumping, build, push, GitHub release creation, and post-publication verification. It keeps `package.json`, root `package-lock.json` top-level version, and `package-lock.json` root package version synchronized. Sequence: require a clean `dev` checkout at `origin/dev` → force the offline-preview build flag and pin all compiled ZCode endpoint aliases to the loopback endpoint → disable Developer ID signing and notarization → bump patch/minor/major → build `ZCode Preview` for current Mac architecture (electron-builder applies the ad-hoc signature in `afterPack`, before DMG/ZIP packaging) → verify the executable-derived app bundle name, exact app version, architecture, bundle identity, offline endpoint, ad-hoc signature, `_TEST` artifact names, archive contents, and hashes → Russian version commit → push `dev` → create a GitHub prerelease pinned to that commit → download the release files and compare hashes and tag target. GitHub's observed release API representation replaces spaces in uploaded asset basenames with dots; metadata and downloaded files are mapped back to the exact local asset pair before their SHA-256 values are compared.

If the push succeeds but release creation or verification fails, rerun `mise exec -- pnpm release:macos:preview:resume <version>` with the exact version printed by the failed run. Resume requires a clean `dev` checkout whose `HEAD` equals `origin/dev`, a commit whose only changed files are `package.json` and `package-lock.json`, synchronized root versions matching the requested version, the matching Russian Preview version commit, the same explicit test endpoint, and the already-built local assets. It never bumps or commits again. Both GitHub's HTTP 404 and the `gh release view` CLI response `release not found` mean that no release exists; other errors remain fatal. An existing tag or release is accepted only when it resolves to that exact commit; a matching complete prerelease is reverified idempotently. If GitHub contains a draft, incomplete release, or release with mismatched metadata/assets, resume stops without publishing or modifying it; inspect and repair or delete that release in GitHub before retrying.

The GitHub token is used only by `gh` for the user's authorized `dev` push and prerelease creation. No Apple credential values are used, inferred, or printed, and none are required; the ad-hoc hook only observes whether the signing-related variables listed above are set. A failed pre-publication gate leaves no release; a failed post-publication verification reports the release URL and failed claim without claiming success.

## Evidence and limitations

The process proves that the exact commit was pushed, that the local Preview app and archives passed structural/version/architecture/ad-hoc-signature checks, and that downloaded release assets match local SHA-256. It does not prove Developer ID signing, notarization, Gatekeeper acceptance, compatibility on other Mac hardware, provider authentication, runtime quality, or PRISM self-improvement. Release notes must state the backend environment and that the build is ad-hoc signed, not Developer ID-signed and not notarized; the note template in `scripts/release-macos-preview.mjs` follows this wording. Cross-platform installers require separate Windows/Linux builds and evidence.
