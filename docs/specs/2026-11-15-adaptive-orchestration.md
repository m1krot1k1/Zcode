# Адаптивная оркестрация волн и обработка claim-конфликтов

Статус: контракт оркестратора обновлён 2026-11-15; правила выбора маршрута уточнены 2026-11-21.

## Обновление 2026-11-21: адаптивный fan-out без лишних уровней

### Наблюдаемая проблема

В сохранённой трассе обычный UI-запрос был отправлен в `start`, затем в `orchestrator`,
затем прошёл отдельные исследовательские, исполнительские, review и repair-волны.
Глобальное правило делегирования требовало вызывать `start` для любой нетривиальной
задачи, а сам `start` запрещал себе выполнять файловую работу. В итоге даже запрос,
который основной агент мог начать сразу, получал обязательный дополнительный уровень.

Параллельность здесь нужна и остаётся включённой. Проблема — повторная передача одной
области между исследователем, исполнителем и повторными проверками, а не количество
независимых исполнителей в одной волне.

### Продуктовые правила

1. **Один небольшой deliverable — основной агент работает напрямую.** Наличие файлов,
   тестов, подходящего профиля или нескольких файлов само по себе не требует `start`,
   `orchestrator` или отдельного subagent.
2. **Реально независимые workstreams запускаются параллельно.** Если ветки уже ясны,
   основной агент запускает точные worker-профили напрямую одним batch. Если сначала
   нужно разложить объём, зависимости или владельца join, основной агент вызывает один
   `orchestrator`, который запускает листья одним batch. Не отправлять одну работу и
   orchestrator-у, и прямым worker-ам. Не вводить жёсткое правило «один» или «два» агентов:
   число веток следует независимым deliverables, runtime ограничивает активные слоты.
3. **Одна ветка владеет своим deliverable от исследования до результата.** Исполнитель
   сам читает нужные факты, вносит изменения и выполняет узкие проверки в своей области.
   Отдельного researcher перед каждым coder не создавать; он нужен, только когда
   независимый read-only ответ сам является deliverable либо конкретная неизвестность
   блокирует исполнение.
4. **Использовать фактический каталог профилей.** Для каждой ветки выбирать точный
   доступный профиль по его специализации. Если подходящий профиль был создан из
   marketplace-навыка, делегировать именно ему; сохранять его привязанный `Skill` и
   право `Task`. Skill-агент может делегировать следующую независимую подзадачу, если
   это действительно уменьшает критический путь и проходит runtime admission.
5. **Динамический fan-out не равен бесконтрольному fan-out.** Число веток определяется
   независимыми deliverables, а не числом файлов и не заранее заданным числом агентов.
   Не создавать ветку без отдельного результата и владельца. Вложенная делегация
   допускается только при новом независимом объёме, которого не было в исходном конверте.
6. **Один обоснованный цикл проверки.** После join выполнить нужные проверки и, если
   риск того требует, один независимый review. Repair запускается только по конкретному
   failed acceptance criterion или воспроизводимому дефекту; исправление получает узкую
   область, а повторно запускаются только затронутые проверки. Не пересоздавать всю
   ветку и не повторять успешные проверки из-за замечаний, не относящихся к ним.
7. **Остановка по доказанному результату.** После успешных acceptance checks завершить
   работу. Если focused repair не устранил тот же дефект, изменить метод или сообщить
   блокер вместо запуска ещё одной одинаковой repair/review-волны.
8. **Детерминированный отказ запуска — не повод для повтора.** Если Task отклонён до
   старта агента из-за отсутствующего аккаунта/модели, недоступного профиля или прав,
   не повторять тот же вызов и не запускать ту же ветку в обход `start`. Сразу вернуть
   точный профиль, выбор модели и причину; повтор допустим только после изменения
   подключения, выбора модели или разрешений.

### Контракт маршрутизации

```text
user request
  ├─ один ограниченный результат / lookup / serial integration ──> root inline
  └─ несколько независимых результатов
       ├─ ветки ясны ──> root: N точных профильных workers одним batch
       └─ нужно разложить зависимости/join ──> один orchestrator
            └─ N профильных веток одним batch по deliverables и runtime capacity
                 ├─ каждая ветка исследует и выполняет свою область
                 └─ вложенный Task только для новой независимой подзадачи
                      ↓
               один join + нужные acceptance checks / review
                    ├─ всё прошло ──> DONE
                    └─ конкретный дефект ──> focused repair → затронутые checks → DONE/blocked
       детерминированный отказ до старта агента ──> точная причина → DONE/blocked
```

`start` остаётся доступен для явного `/start` и для маршрутизации, когда это действительно
полезно. Глобальное always-apply правило не должно принудительно запускать его для каждой
задачи. Искусственные L1–L4 поля и самопроверку глубины Task-цепочки не добавлять. Роутер
не подменяет выбор профильных marketplace-агентов универсальным `coder`.

### Приёмочные сценарии обновления

1. Небольшой single-deliverable запрос в системной инструкции остаётся у root и не требует
   вызова `start` или `Task` только из-за наличия файлов/тестов/доступного профиля.
2. Несколько независимых deliverables назначаются точным профилям одним batch; root
   использует orchestrator только если нужны декомпозиция/планирование зависимостей/join.
   Число веток не ограничено фиксированными 1–2 и не превышает реальную runtime capacity.
3. Ветка по умолчанию не создаёт отдельный researcher для того же deliverable перед
   исполнителем.
4. Точный подходящий skill-backed профиль виден в каталоге и может быть выбран как worker;
   он сохраняет привязанный skill и может делегировать собственную новую независимую
   подзадачу.
5. Успешные checks завершают волну; конкретный дефект даёт одну узкую repair-ветку и
   повтор только затронутых checks.
6. Existing `write_claim_conflict`, пользовательская отмена, права и capability grants
   продолжают работать по существующим правилам ниже.
7. Отказ точного marketplace-профиля по `account-connection-unavailable` не вызывает
   второй такой же Task и не переключает запуск с `start` на root; отчёт показывает
   точный `subagent_type` и недоступный `provider/model`.
8. Один ограниченный lookup из `start` маршрутизируется одним Task сразу точному
   профильному агенту. Неясность без подтверждённых независимых результатов сама по себе
   не создаёт `orchestrator`.
9. Skill-backed профиль прекращает работу с `blocked` и точной ошибкой, если не смог
   загрузить обязательный Skill; он не продолжает без специализации и не подменяет профиль.
10. `code-search` при сбое CodeIndex делает один узкий поиск через нативные Grep/Glob
    с ограниченным каталогом/типом файлов; он не запускает широкий Bash `rg` из корня.
    Зависшее подтверждение permission не считается выполненной веткой.

## Проблема

Прогон 2026-11-15 показал два разрыва:

1. Оркестратор запускал заранее перечисленные ветки; один `Task` был отклонён
   work-ledger'ом с `write_claim_conflict` («another agent holds an overlapping file
   path… The spawn was not started»). Ветка не была перезапущена и не была
   перепланирована — оркестратор продолжил ждать остальные ветки.
2. Новый пользовательский ввод отменил родительский turn. Runtime пометил `start`,
   `orchestrator` и `backend-coder` как `killed` («Background agent task stopped»,
   `Turn was cancelled`). Отмена терминальна: дочерние задачи не перезапускаются
   автоматически. Это ожидаемое поведение для отмены, но оно не должно маскироваться
   под «агент упал и сам восстановился».

## Продуктовые правила

1. Отчёт каждой ветки — вход для решения оркестратора, а не финал. После терминала,
   `partial`/`blocked` или новых unknowns оркестратор пересматривает план и при
   необходимости запускает следующий конверт, не дожидаясь остальных заранее
   перечисленных веток.
2. `write_claim_conflict` означает, что ветка **не запущена**. Её нельзя считать
   выполненной и нельзя повторять тот же вызов. Нужно сузить `write_paths` до
   непересекающихся файлов либо отложить спавн и повторить после терминала держателя
   claim.
3. Две writer-ветки с пересекающимися `write_paths` одновременно не запускаются;
   read-only ветка всегда передаёт `write_paths: []`.
4. Недостающий skill/MCP/plugin — отдельный шаг: установка/подключение через
   `SkillSearch`/`SkillInstall` или штатные средства окружения, подтверждение, затем
   использование. Нельзя подменять возможность общими рассуждениями.
5. Отмена пользователем терминальна: runtime убивает дочерние задачи и не делает
   автоматический restart/repair. Repair-волна допустима только для реального
   `failed`/`blocked`, а не для `cancelled`.

## Владелец состояния и порядок событий

```text
orchestrator (Task-only)
  ├─ Task(worker) ──> work ledger admit
  │                     ├─ claimed ──> worker runs ──> terminal report
  │                     └─ write_claim_conflict ──> spawn rejected (branch not started)
  │
  ├─ terminal report / conflict
  │       │
  │       └─ reassess: narrow write_paths | defer until holder terminal | next wave
  │
  └─ user cancel ──> runtime kills children (terminal "killed"); no auto-restart
```

## До / после

| Сценарий                  | До                  | После (контракт)                         |
| ------------------------- | ------------------- | ---------------------------------------- |
| `write_claim_conflict`    | ветка потеряна/ждём | сузить пути или отложить и повторить     |
| Ветка вернула partial     | ждём остальные      | сразу следующий конверт по необходимости |
| Нужен отсутствующий skill | общие рассуждения   | явный шаг установки + evidence           |
| Пользователь отменил turn | killed              | killed, без автоматического restart      |

## Acceptance-сценарии

1. Конфликт claim → оркестратор не объявляет ветку выполненной, меняет `write_paths` или
   ждёт держателя и повторяет спавн.
2. После отчёта одной ветки разблокирована следующая → оркестратор запускает её, не
   ожидая терминала остальных.
3. Отмена пользователем → терминалы `killed`, отчёт честно фиксирует отмену, а не
   «агент восстановился».

- Интеграционный прогон с claim-конфликтом требует живого runtime; targeted tests и

### Nested skill-backed profiles

- A child profile may load an exact skill declared in its own profile when every ancestor allowlist permits that skill. Ancestor `preferredSkills` only controls each ancestor's visible catalog and must not hide a child's declared skill.
- A child may not load a skill denied by any ancestor allowlist; this remains fail-closed even when the child profile declares that skill.
- If a profile declares a skill but the inherited catalog cannot discover it, the error must distinguish catalog unavailability from an allowlist denial. It must not describe this as a general subagent Skill ban; it should point to the active workspace skill roots and ancestor allowlists.
