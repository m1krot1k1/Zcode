# Батчинг независимых tool-вызовов и агентов

| Поле      | Значение                                                                                                                   |
| --------- | -------------------------------------------------------------------------------------------------------------------------- |
| Статус    | Реализовано (промпт + описание Task); эффект требует замера на реальном прогоне                                            |
| Дата      | 2026-11-12                                                                                                                 |
| Источник  | Анализ логов `~/.zcode/cli/log/zcode-2026-11-1{1,2}.jsonl` (14 655 шагов модели)                                           |
| Область   | `apps/zcode-cli/packages/core/src/context/sections/identity.ts`, `apps/zcode-cli/packages/core/src/tool/handlers/agent.ts` |
| Регрессия | `apps/zcode-cli/packages/core/tests/context-builder.test.ts`                                                               |

## 1. Измеренная проблема

За два дня работы агентных прогонов зафиксировано 14 655 шагов модели и 28 741 tool-вызов,
то есть **1.96 вызова на шаг**. Распределение: 32% шагов содержат ровно один вызов,
а 0.6% шагов не содержат вызовов вовсе.

Стоимость шага растёт с числом вызовов нелинейно в пользу группировки: медиана 6.7 с на
одном вызове, 8.6 с на двух, 12.1 с на трёх, 16.7 с на четырёх. Один шаг — это один
сетевой round-trip: отправка всего контекста, ожидание, стриминг. Три вызова в одном
ответе дешевле трёх отдельных ответов.

Арифметика верхней границы: при 3.0 вызова на шаг вместо 1.96 число шагов падает
с 14 655 до ~9 580 (−35%), а модельное время — на ~54 ч из 157 ч.

Отдельно: 73 из 90 измеренных часов tool-времени приходятся на `Task` — ожидание
субагентов. Это не вычисления, а простой, если агенты запускаются по одному.

## 2. Что изменено

**Harness-блок системного промпта.** Прежняя формулировка была разрешением:
«Independent tool calls can run in parallel in one response». Заменена на требование
с явным критерием зависимости: если вызов не нуждается в результате другого вызова —
оба идут в одном ответе; Read/Grep/Glob/CodeIndex/Bash-инспекция по разным путям
считаются независимыми по умолчанию; сериализация только при реальной зависимости
(Read перед Edit того же файла, команда с путём из предыдущего вызова).

Добавлен запрет на «пустой» шаг: если следующее действие уже определено, tool-вызов
идёт в том же ответе, а не после текста-анонса. Основание: шаги без вызовов имеют
медиану 25.5 с против 6.7 с у шагов с одним вызовом.

**Описание инструмента Agent/Task.** Добавлен абзац о батчинге: два и более агента,
чьи входы не зависят друг от друга, запускаются несколькими `Task`-вызовами в одном
ответе. Зависимые агенты остаются в следующем ответе. Указана измеренная цена
последовательного ожидания.

## 3. Что сознательно не сделано

Профиль PRISM не менялся. Доступен `coding` (3 модуля, 15 132 символа) вместо `all`
(6 модулей, 24 584 символа), что сэкономило бы ~2 900 токенов на запрос, но профиль
`coding` убирает модуль SWARM EXECUTION — тот самый, который требует не блокировать
READY-ветви. Экономия промпта противоречила бы цели ускорения за счёт параллелизма.
Профиль остаётся `all`, гейт `node scripts/prism10-runtime-profile.mjs --check` зелёный.

## 4. Критерии приёмки

- BN-01: Harness-блок содержит требование батчинга и критерий зависимости.
  Проверка: `context-builder.test.ts` (стабильный system body).
- BN-02: Описание Agent содержит правило батчинга независимых агентов.
  Проверка: code review + присутствие строки в provider-visible описании.
- BN-03: PRISM-профиль остаётся валидным. Проверка: `prism10-runtime-profile.mjs --check`.
- BN-04: Эффект измеряется по `context.toolCallCount` в `model.request.completed`:
  ожидается рост среднего числа вызовов на шаг выше 1.96 при неизменном качестве
  выполнения задач. Проверка: сравнение логов до/после на сопоставимой задаче.

## 5. Риски

Требование батчинга может привести к выдаче вызовов, которые фактически зависят друг
от друга (например Read и Edit одного файла в одном ответе). Критерий зависимости
прописан явно, а dependency-планировщик (`tool/scheduler.ts`) всё равно сериализует
вызовы с объявленными зависимостями. Основной риск — не поломка, а неполное
соблюдение инструкции моделью; это проверяется метрикой BN-04.
