# cli-auto-repair-loop

Детерминированный замкнутый цикл самовосстановления: `Action → Telemetry → Invariant Gate → Diagnosis → Repair → Re-verify`.

Владелец состояния — `AutoRepairLoop`: итерации, бюджет времени, история сигнатур.
Сам цикл **не выполняет** typecheck/lint/тесты — порты внедряются вызывающим (`RepairVerificationPort`),
поэтому ядро не зависит от конкретных исполнителей и остаётся тестируемым.

## Инварианты

1. **Детерминированный порядок.** Сигналы сортируются по `(severity, source, file, line, code, message)`.
   Одинаковый набор вердиктов даёт одинаковый `report` и одинаковый `signatureHistory`.
2. **Дедупликация с усилением.** Один и тот же дефект из разных портов схлопывается в один сигнал;
   `blocking` побеждает `warning` (нельзя понизить серьёзность порядком поступления).
3. **Жёсткие лимиты.** `maxIterations` (4), `maxElapsedMs` (5 мин), `maxSignalsPerIteration` (20).
   Лимит проверяется **до** запуска проверки: исчерпанный бюджет не тратится впустую.
4. **Защита от осцилляции.** Одна и та же сигнатура подряд `repeatThreshold` (2) раза останавливает
   цикл с `oscillation-detected`/`repeated-error` и предлагает пересмотр гипотезы через CodeIndex.
5. **Падение порта видно.** Исключение внутри проверки превращается в блокирующий сигнал `tool-call`,
   а не в «проверка прошла».
6. **Усечение явно.** Если сигналов больше бюджета, флаг `truncatedSources` содержит источники,
   попавшие под усечение.
7. **Внешний предохранитель.** `runAutoRepairLoopToCompletion` имеет собственный жёсткий предел
   32 итерации — ошибка в самом цикле не может привести к бесконечному выполнению.
8. **По умолчанию выключен.** В агентный ход цикл подключается флагом; поведение 4.1 не меняется.

## Пересечения

- `ToolCallSelfRepair` (4.1): источник сигналов `tool-call`.
- `cli-exec-sandbox`/`cli-exec-pty` (4.5a): источник `pty`.
- stateful Playwright-контроллер (`cli-browser-telemetry`, 4.5b): источники `browser-*`.
- Транзакции (4.2): источник `file-state`.
